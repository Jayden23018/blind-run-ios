## 1. 背景

### 1.1 用户

- **视障跑者**：跑步时手机绑在手臂上，戴骨传导耳机，依赖 VoiceOver，几乎不看屏幕。
- **陪跑员**：有视力的志愿者，用引导绳牵引跑者一起跑。跑步时一只手握绳、眼睛看路，手机多在口袋或臂包里。后端规定只有陪跑员能结束服务。

### 1.2 设计语言（与跑者端一致，必须保持）

- 订单一个页面贯穿全流程，状态在原页面原地变化，不跳页。
- 订单页底部只有“一个黄色主按钮 + 求助与安全”，不并排放多个按钮。每屏最多一个黄色控件。实心红只用于紧急求助。
- 只放用得上的信息。正常状态不提示，出现异常才提示。
- 深色模式跟随系统，支持动态字体，陪跑员端也要完整支持 VoiceOver（可能有低视力志愿者，也是 App Store 无障碍要求）。

| Token | 值 | 用途 |

| 背景 | 浅灰（跑者端现有值，草图用 #F2F3F7） | 页面背景 |

| 品牌蓝 | #2A5BD7 | 进度、链接、图标 |

## 2. 决策汇总

### 2.1 产品负责人确认的背景

| 项 | 结论 |
|---|---|
| 运营主体 | 已登记的志愿服务组织 |
| 陪跑员年龄 | 仅限 18 岁以上 |
| 准入 | 强制两步：实名认证、线上课程。线下见习和签志愿者协议不放进 App 准入流程 |
| 主页与接单 | 分开。打开 App 先到主页看自己的贡献，滑动后进入接单 |
| 接单主页 | 以“下一次陪跑”深蓝卡为主 |
| 空闲时间等设置 | 从首页移到“我的” |
| 邀请、订单页、异常 | 按 v1 草图执行 |
| 滑动开始接单 | 保留滑动手势（陪跑员多数不用 VoiceOver）；仍为滑块加 VoiceOver 双击操作，无视觉成本 |
| 新邀请呈现 | 需要成熟方案，参考同类产品（见 §4.4） |

### 2.2 沿用的已拍板决定（来自跑者端与《跑步中设计方向》）

- 开始跑步：双方都能按，先按的生效；不做暂停。
- 陪跑员跑中：主按钮“结束陪跑”长按 2 秒；语音播报默认关闭，用震动 + 画面提示；不做地图；锁屏实时活动只显示数据，不放结束按钮。
- 走散时先提醒陪跑员，陪跑员 30 秒未确认才提醒跑者；陪跑员端显示跑者手机电量 ≤20% 的提示。
- 陪跑员看不到跑者的单条评价（“有问题”永不展示），也看不到跑者的任何求助操作（“联系陪跑员”除外）。
- 陪跑员不给跑者打分，只能“上报问题”。
- 跑后显示“本次志愿服务时长”。
- 倾向方案：跑中主卡改为深蓝底白字，两端共用。

### 2.3 本轮设计决策

| 决策 | 内容 | 原因 |
|---|---|---|
| 匹配模式 | 系统在陪跑员空闲时间内定向邀请，一起跑过的陪跑员优先；等 3 小时无人接，进入“附近还没人接的”列表 | 陪跑是预约单，要到场 1 小时以上；广播抢单会让输家挫败，冲动接单后容易爽约 |
| 回复期限 | 距开始超过 24 小时给 1 小时，否则给 15 分钟；不做秒级倒计时 | 陪跑员需要判断“那天能不能去”，倒计时诱发冲动接单 |
| 接单前隐私 | 只显示姓氏、视力情况、距离与配速、引导习惯；全名、电话、实时位置接单后才显示 | 给够判断信息，避免跑者信息外泄 |
| 订单页步骤 | 邀请 → 约好 → 出发 → 汇合，与跑者端“匹配 → 约好 → 出发 → 汇合”一一对应 | 两端组件同构，便于复用 |
| 汇合方式 | 陪跑员去找跑者，显示跑者方位、距离、当天衣着 | 全盲跑者自己找到集合点、认出陪跑员很难；线下跑团也是专人接送 |
| 到达判定 | 进入集合点 100 米内推送询问，由陪跑员手动确认，不自动判定 | 网约车自动到达有误报；对视障跑者，“已到达”误报的代价很大 |
| 取消 | 开始前 12 小时内取消记一次临时取消；30 天内满 3 次，14 天不收邀请；记录不展示给跑者 | 参考 Achilles 的 12 小时规则；只影响匹配，不做公开惩罚 |
| 迟到与等待 | 预计晚到超过 3 分钟自动通知跑者；陪跑员到达后等满 15 分钟可结束等待，不算陪跑员责任 | 陪跑员在路上不方便打字 |
| 时长口径 | 从开始跑步到结束陪跑，按 0.1 小时取整，显示“待认证”，组织 10 个工作日内确认 | 《志愿服务记录与证明出具办法》规定由组织确定实际服务时间，10 个工作日内记录 |
| 文案红线 | 全 App 不出现升学、加分、评优等字样 | 2026 年网信办、中央社会工作部专项整治涉及此类宣传 |
| 新邀请呈现 | 按陪跑员当下状态分四档：后台推送 / 接单主页底部邀请卡 / 其他页面顶部横幅 / 陪跑进行中暂存 | Uber、DoorDash 用全屏或底部邀请卡；苹果规范要求 App 在用时以不打断的方式呈现；DoorDash 配送途中静音非必要通知 |
| 激励 | 主页展示陪跑次数、已认证时长、一起跑过的跑者数、奖章；不做排行榜、里程荣誉、积分兑换 | 详见 §7 |

## 3. 调研摘要（结论与启示）

| 主题 | 发现（信息日期） | 对助盲跑的启示 |
|---|---|---|
| Be My Eyes | 求助同时推给多名志愿者，先接先得；志愿者约为用户的 10 倍，很久接不到是常态；有志愿者抱怨总被别人抢先（2025–2026） | 秒级抢单只适合几分钟的线上任务，不适合要到场的陪跑；“没单”要做成不打扰的常态 |
| Aira | 付费全职视觉翻译员，卖点之一是不用消耗亲友人情（2026-07） | 求助本身有心理成本：跑后不强制跑者感谢 |
| United in Stride | 自助目录：建档、按地区/配速/距离搜索、私信；建议新搭档先短跑并做基础训练（2024） | 配速、距离是陪跑员判断接不接的核心字段 |
| Achilles International | 背景调查、培训视频；按运动员偏好、配速配对；提前 12 小时报名或取消；分会要求见习后才单独配对 | 12 小时取消窗口；固定搭档优先 |
| Guiding Eyes | Running Guides 是训练导盲犬陪跑，不是人与人匹配（2022–2026） | 反证：人工陪跑的协调成本是跑者的主要障碍 |
| 国内跑团 | 何亚君助盲团、深圳 U 跑团（近 600 人）、黑暗跑团深圳站等，均为固定时间地点团跑 + 人工调度；盲友普遍不爱提意见；需要专人接送；学生流动大（2024–2026） | 1 对 1 预约是新模式；汇合应由陪跑员去找人；跑者的反馈渠道要低门槛 |
| 志愿时长 | 记录主体是志愿服务组织；志愿深圳是深圳本地平台，i志愿为广东省平台；志愿汇不允许补录（2020–2026） | 时长由组织确认后同步；App 内先标“待认证” |
| 网约车交互 | Uber 接单 15 秒、到达后通知乘客并计时、有预设消息；自动到达有误报；滴滴预约单按住址算距离（2018–2025） | 距离按陪跑员出发地算；到达手动确认；快捷消息 |
| 激励研究 | 被迫做志愿会降低以后继续的意愿（Stukas 1999）；金钱报酬可能减少志愿时长（Frey & Goette 1999），但也有研究未发现挤出（2023）；视障跑者因失去自主离开陪跑教练（2022）；学生志愿时长买卖问题（人民日报 2026-03） | 激励要避免“控制感”和“把人当数量”；不做兑换和排行 |
| 派单呈现（v3 补充） | Uber 区分“只发给你、限时接受”的邀请和“发给多人、先匹配先得”的 Trip Radar 列表；预约单最多提前一周可见，拒绝预约单不影响接单率（2023–2025）。DoorDash 邀请到来时推送 + App 内邀请页，50 秒决定；配送途中只保留必要通知，到达后再显示其他（2023）。美团众包“系统派单 + 大厅抢单”双模式，并语音播报订单（2026）。苹果规范：App 在用时，把新信息以不打扰的方式插入当前界面；通知详情最多 4 个操作；时间敏感通知首次出现时系统会询问用户是否保留 | 定向邀请 = Uber 独享邀请，“附近还没人接的” = Trip Radar；不重复响铃；陪跑中暂存；推送只放 2 个操作；时间敏感级别只给 24 小时内开始的邀请 |
| 准入与安全 | 《志愿服务条例》要求招募时告知风险、需技能的先培训、可能有人身危险的活动要为志愿者买意外险（2017） | 风险告知放进实名认证步骤；保险由组织在后台确认生效后才发邀请 |

## 4. 信息架构与界面规格

### 4.1 导航结构

底部标签栏与跑者端相同：**首页 / 记录 / 我的**。

首页标签内，根据状态决定显示哪一屏：

```
打开 App
├─ 未完成准入 ─────────────────────────→ [S1 准入]
├─ 有进行中订单（已出发 / 汇合 / 跑步中）
│  或 2 小时内开始的陪跑 ───────────────→ [S6 订单页]
└─ 其他 ───────────────────────────────→ [S2 主页]
                                          │ 滑动“开始接单”
                                          ▼
                                  [S3 接单主页（有约）]
                                  [S4 接单主页（暂无约）]
                                   ├─ 新邀请 → [S5 邀请 = S6 订单页“邀请”状态]
                                   ├─ 附近还没人接的 → [S5b 列表] → S6
                                   ├─ 空闲时间 → 跳到 我的 › [S7]
                                   └─ 暂停接单（二次确认）→ 回到 S2

我的 › 空闲时间与出发地 → [S7]
推送“新的陪跑邀请” → 直接打开 S6（邀请状态）
```

“接单中”（`isAcceptingInvites`）是服务端保存的账号状态。开启后一直保持，直到陪跑员暂停；每次打开 App 仍先显示 S2 主页。只有在“接单中”且处于空闲时间内，才会收到邀请。

### 4.3 逐屏细节

#### S1 准入

- 两步都完成前，S2、S3、邀请推送一律不可达。
- 实名认证步骤内包含：志愿者须知、风险告知的阅读与勾选；年龄校验（身份证未满 18 岁直接提示“陪跑员需年满 18 岁”，不可继续）。
- 两步完成后，还需等组织在后台确认保险生效，才开始发邀请。这段时间 S2 正常显示，滑块可用，接单主页显示提示条“组织正在为你办理志愿者保险，完成后开始收到邀请”。
- 读屏顺序：问候 → “第 2 步，共 2 步，线上课程，已学 3 节” → 主按钮。

#### S2 主页

- 数据：陪跑次数（已完成订单数）、已认证志愿服务时长（小时，一位小数；待认证的不计入这里）、一起跑过的不同跑者数、奖章（按获得时间倒序，最多 4 枚）、最近一次陪跑（日期、跑者名、距离）。
- 新用户 0 次时：大号数字处显示“还没有陪跑”，统计格和奖章行隐藏，只保留滑块。
- **滑块无障碍**：VoiceOver 下整个滑块是一个按钮元素，`accessibilityLabel`“开始接单”，`accessibilityHint`“双击开始接单”，双击直接生效；同时满足动态字体放大后仍单行或自动换两行、不截断。关闭“减弱动态效果”以外不要加额外动画。
- 滑动完成：轻震一次 → 服务端置为接单中 → 进入 S3/S4。失败则回弹并提示“没有开启，检查网络后再试”。
- 手势说明：陪跑员多数不使用 VoiceOver，滑动手势是主要交互；VoiceOver 双击只是附加的无障碍操作，不改变视觉。
- 读屏顺序：问候 → “陪跑 32 次” → “志愿服务时长 26.4 小时，已认证” → “9 位跑者和你一起跑过” → 奖章 → 最近一次 → 开始接单。

#### S3 / S4 接单主页

- 深蓝卡复用跑者端“下一次陪跑”卡：人物行由“陪跑员 张伟 / 陪跑 32 次，引导绳经验 2 年”换成“跑者 李明 / 你们一起跑过 N 次”（首次显示“第一次一起跑”）。
- 新邀请卡复用跑者端“预约新的陪跑”浅蓝卡：图标换铃铛，标题“N 个新邀请”，副标题为最早一条的时间、地点、回复期限。
- “暂停接单”点击后弹出确认：“暂停后不会收到新邀请，已约好的陪跑不受影响。”按钮：黄色“保持接单”，灰色文字“暂停”。
- 读屏顺序：接单中 → 下一次陪跑 → 新邀请 → 附近没人接 → 暂停接单 → 标签栏。

#### S5 邀请（S6 的“邀请”状态）

- 进度第 1 步“邀请”高亮。
- hero：跑者姓氏首字头像；标题“周六 7:00”；副标题“深圳湾公园 3 号入口，离你约 3.2 公里 / 请在今晚 22:00 前回复”。
- 列表：跑者“李先生 / 全盲，用引导绳”；跑多远“5 公里 / 配速 7 分左右”；引导习惯“陪跑员在左侧 / 过台阶提前说一声”；“这次去不了 ›”。
- 按钮上方小字“接下后显示李先生的全名和电话”；主按钮“接下这次陪跑”。此状态不显示求助与安全。
- “这次去不了”直接生效，不问原因、不计任何记录，返回上一页。
- 邀请已被他人接下或过期：页面原地变为“这次陪跑已经有人接了”，主按钮“回到接单”。
- 从 S5b 列表进入时，同一模板，没有“请在……前回复”。

#### S6 订单页各状态

见 §5。视觉以 `png/03-订单页全流程.png` 和 `png/04-取消迟到爽约.png` 为准。

#### S7 空闲时间与出发地

- 空闲时间：按周重复的时间段，可增删改；至少保留 1 段，否则不发邀请并在 S4 显示“还没设置空闲时间 ›”。
- 出发地：地图选点或输入地址，只用于计算距离和出发时间，不对跑者展示。
- 常用交通：步行 / 骑车 / 公共交通 / 开车。
- 愿意去多远：3 / 5 / 10 / 20 公里以内。

### 4.4 新邀请进来（v3 新增）

视觉参考：`png/02-新邀请进来.png`。

#### 4.4.1 按陪跑员当下状态决定呈现方式

| 陪跑员当下 | 呈现方式 | 声音 / 震动 | 点按后 |
|---|---|---|---|
| App 在后台或锁屏 | 系统推送。24 小时内开始的邀请用 Time Sensitive 级别，其余用 Active 级别 | 系统默认一次，不重复 | 打开 App → 接单主页 → 弹出邀请卡 |
| 长按推送 | 展开详情 + 2 个操作：“接下这次陪跑”（需要解锁，`authenticationRequired`）、“这次去不了”（`destructive`） | — | 接下成功后发一条本地通知“已约好”；失败（已失效）则提示“这个邀请已失效” |
| App 在前台，位于接单主页 | 底部邀请卡（sheet，约 2/3 高度），背景压暗 | 轻震一次 + 短提示音一次（跟随静音开关） | — |
| App 在前台，位于其他页面（主页、我的、记录、订单页“约好”状态） | 顶部横幅，4 秒后收起；首页标签加数字角标 | 轻震一次，无声音 | 点“查看”弹出邀请卡 |
| 有进行中的陪跑（已出发 / 汇合 / 跑步中 / 等待中） | 不推送、不横幅、不震动，暂存 | 无 | 陪跑结束回到接单主页后，以“陪跑时收到 N 个新邀请”卡片出现 |
| 未开启接单 / 空闲时间以外 / 22:00–6:00 | 后端不发邀请 | — | — |

后端规则：会在陪跑员当前陪跑结束前过期的邀请，不发给这位陪跑员；与已约好陪跑时间重叠的邀请不发。

#### 4.4.2 邀请卡（新建组件 `InviteSheet`）

从上到下：

1. 拖动条
2. 标题行：左“新的陪跑邀请”（多个时“N 个新邀请” + 分页点）；右“还剩 X 分钟回复”（超过 60 分钟显示“今晚 22:00 前回复”这类绝对时间）
3. 回复进度条（3pt，剩余时间占比；剩余 < 15 分钟变深黄 #D99A00，文字加粗变 #8A5A00）
4. 时间（大号，28pt 粗体）
5. 集合点名称
6. 三格数据：离你 X 公里 / 跑多远 X 公里 / 配速
7. 跑者行：头像首字、姓名、视力与引导习惯；一起跑过的跑者显示全名和标签“一起跑过 N 次”，首次合作只显示“李先生”
8. 条件提示条（浅黄）：与已约好陪跑之间留给赶路的时间不足 30 分钟时出现，例如“你周六 6:00 在深圳湾的陪跑预计 6:50 结束，赶过来约 25 分钟”
9. 黄色主按钮“接下这次陪跑”
10. 两个文字按钮：左“这次去不了”，右“查看详情”（进入 S6 邀请状态完整订单页）

交互：

- 下滑或点背景：收起，不算回复，邀请留在接单主页的新邀请卡里。
- 多个邀请：按回复期限升序；同等期限下一起跑过的跑者优先；左右滑动切换；回复一个后自动切到下一个，全部回复完自动收起。
- 读屏：打开时焦点在标题行，顺序为 标题 → 剩余时间 → 时间 → 地点 → 三格数据 → 跑者 → 提示条 → 主按钮 → 去不了 → 查看详情。

#### 4.4.3 邀请卡的结果状态（原地变化，不关闭再弹新弹层）

| 结果 | 卡片变化 | 其他 |
|---|---|---|
| 接下成功 | 内容替换为绿色勾、“已约好”、时间地点、“李明的全名和电话已放进订单”；主按钮“查看订单”，文字按钮“回到接单” | 成功震动；接单主页更新“下一次陪跑”或“之后还有 N 次陪跑”；通知跑者 |
| 接下失败：已过期 | 内容变灰，标题“这个邀请已失效”，说明“回复时间已过” | 主按钮“知道了” |
| 接下失败：被别人接（从附近列表进入时） | 同上，说明“已经有其他陪跑员接下了，没有影响你的任何记录” | 主按钮“知道了” |
| 这次去不了 | 卡片收起（多个邀请时切到下一个） | 底部 toast“已回复这次去不了 / 撤销”，5 秒内可撤销；连续 3 次去不了后，下次打开接单主页询问“要不要调整空闲时间”，不做任何惩罚 |
| 在卡片打开期间过期 | 进度条走完后原地变为“这个邀请已失效” | 无推送 |

#### 4.4.4 “附近还没人接的”与邀请的区别

| | 邀请 | 附近还没人接的 |
|---|---|---|
| 类比 | Uber 只发给你的限时邀请 | Uber Trip Radar |
| 来源 | 系统定向发给这位陪跑员 | 等待 3 小时无人接的单，所有合适的陪跑员可见 |
| 提醒 | 按 4.4.1 呈现 | 不推送，只在接单主页显示入口 |
| 回复期限 | 有 | 无，先接先得 |
| 失败文案 | 已过期 | 已经有其他陪跑员接下了 |

## 5. 订单页状态机（陪跑员端 ↔ 跑者端）

| 陪跑员端状态 | 进入条件 | hero 标题 / 副标题 | 列表内容 | 陪跑员主按钮 | 跑者端对应 |

| 邀请 | 系统发出邀请 | 周六 7:00 / 地点、距离、回复期限 | 跑者（姓氏）、跑多远、引导习惯、这次去不了 | 接下这次陪跑 | 正在匹配陪跑员 |

| 出发 | 按“我出发了” | 8 分钟后到 / 李明已到 3 号入口附近（或“李明还在路上”） | 导航去集合点 ›（跳系统地图）、给李明发语音消息 ›、修改或取消 › | 我已到达集合点 | 陪跑员赶来中 |
| 出发（晚到） | 预计晚到 > 3 分钟 | 晚到约 6 分钟 / 7:06 左右到…… | 浅黄提示条“已自动告诉李明你会晚到约 6 分钟” + 同上 | 我已到达集合点 | 陪跑员赶来中，播报晚到 |

| 汇合（等待超时） | 到达后满 15 分钟未开始 | 你已等了 15 分钟 / 李明还没到，手机位置在 1.8 公里外 | 打电话给李明 › | 结束等待（上方小字“结束后不算你的取消，时长不计入”） | 待定（跑者端需补） |
| 跑步中 | 任一方按“开始跑步” | 深蓝主卡：距离、用时、配速 | 跑者、目标、遇到问题 › | 长按 2 秒，结束陪跑 | 跑步中 |
| 已完成 | 陪跑员结束 | 陪跑完成 / 和李明跑了 5.12 公里，用时 39 分 20 秒 | 时长卡“本次志愿服务时长 0.7 小时 · 待认证”；查看跑步记录 ›、上报问题 › | 完成 | 已完成 |
| 跑者已取消 | 跑者取消 | 李明取消了这次陪跑 / 不算你的取消，不需要做什么 | 时间、集合点（半透明） | 回到首页（此状态无求助与安全） | — |
| 陪跑员取消确认 | 点“修改或取消 › 取消” | 底部弹层“取消这次陪跑？” | 12 小时内：说明会记临时取消并为跑者重新找人，以及 3 次/30 天规则；12 小时外：只问是否确认 | 保留这次陪跑（黄）/ 仍然取消（灰字） | 重新进入匹配 |

实现要点：

- 状态变化时原地替换 hero 与列表内容，进度条延伸，主按钮文字切换；不 push 新页面。
- 汇合状态的方位指示：根据跑者上报位置与手机朝向实时旋转；距离 < 10 米时轻震一次；跑者位置超过 60 秒未更新时，改为显示“李明的位置暂时没有更新”。
- 状态变化时，若 VoiceOver 开启，用 announcement 读出新的 hero 标题（如“李明在你右前方，约 40 米”）。VoiceOver 关闭时不发声音。
- 长按 2 秒结束：VoiceOver 下提供自定义操作“结束陪跑”，触发后弹确认框。
- “开始跑步”双方都能按，服务端以先到的请求为准，后到的一方直接切到跑步中。

## 7. 激励方案

**做：**

- 主页统计：陪跑次数、已认证志愿服务时长、一起跑过的跑者数。
- 奖章：首批只做 完成培训、首次陪跑、陪跑 10 / 30 / 100 次、固定搭档（和同一位跑者跑满 5 次）。
- 接单主页和订单页里的“你们一起跑过 N 次”。
- 年度志愿服务记录证明，由组织出具。
- 跑者主动留言时，在已完成页多出一行“李明给你留了话”。

**不做：**

- 排行榜、里程或配速荣誉（与“按跑者节奏跑”冲突）。
- 积分兑换、物质奖励。
- 按“帮助过多少人”发奖章（会鼓励频繁换跑者，与固定搭档冲突）。
- 跑后默认弹出“请跑者感谢”。
- 任何升学、加分、评优字样。

**提醒：** 主页上的“一起跑过的跑者数”按产品负责人要求保留，措辞用“位跑者和你一起跑过”，不用“帮助了多少人”，避免把跑者表达成被帮助的数量。

## 8. 需要跑者端和后端配合

**跑者端：**

1. “已约好”阶段增加“出门前选择当天衣着颜色”，全 VoiceOver 可操作，结果显示在陪跑员汇合页。
2. 汇合文案从“请提前 10 分钟到达”改为“到入口附近停下即可，张伟会来找你”。

4. 陪跑员“结束等待”后跑者端的显示与播报（待设计）。
5. 下单时的字段需覆盖：视力情况、距离、配速、引导方式、引导习惯备注。

**后端：**

1. 陪跑员账号：准入状态（实名、课程进度）、年龄校验、保险生效标记、`isAcceptingInvites`、空闲时间段、出发地、交通方式、接单半径。

6. 临时取消计数与暂停邀请规则（参数见 §10）。
7. 统计：陪跑次数、已认证时长、一起跑过的跑者数、奖章发放。
8. 时长：以服务端开始、结束时间计算，状态“待认证 / 已认证”，按组织确认结果同步到志愿服务记录平台。

## 11. 风险与待确认

1. **志愿者意外险**：《志愿服务条例》第十七条要求组织在安排可能有人身危险的活动前为志愿者购买意外伤害保险。准入流程已去掉“签协议”，因此需要组织在后台确认投保生效后才发邀请（§4.3 S1 已设计该中间态）。需组织确认投保方式。
2. **线下见习移出准入**：调研中的国内外组织都要求单独带跑前有线下见习或跟跑。去掉后，建议至少让陪跑员的首次陪跑只匹配“愿意和新陪跑员跑”的跑者，由跑者端下单时勾选。待产品负责人决定。
3. **时长口径**：是否包含汇合等待时间，需组织确认。
4. **跑者端“结束等待”后的状态**：未设计。
5. **《跑步中设计方向》** 未包含在本次交付中，跑中页以代码库现有实现和该文档为准。
6. **未设计的页面**：陪跑员端“记录”、“求助与安全”的具体选项、奖章详情、线上课程播放页。实现时先留占位，不要自行设计。
