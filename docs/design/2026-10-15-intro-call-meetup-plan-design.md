## 1. 状态与数据

**订单状态白名单不加新值。** 改约全程发生在 `PENDING_INTRO_CALL` 之内，新增的是挂在「这一轮通话」上的一张**见面安排单**（下称「安排单」）。

### 1.1 子状态（客户端由 `GET /intro-call` 推出，不是订单状态）

| 子状态 | 判据 | 盲人端 | 陪跑员端 |
|---|---|---|---|
| ① 待通话 | 无安排单，盲人本轮未从电话回来 | B1 | V1 |
| ② 聊过了 | 无安排单，盲人 App 从**后台**回到前台 | B2 | V1 |
| ③ 安排待确认 | 有安排单，盲人未确认最新版本 | B3 | V3 |
| ④ 约好 | 盲人确认最新版本，后端成单 | 订单页「约好」 | 订单页「约好」 |
| 出口 | 不合适 / 没打通 / 超时 / 盲人取消 | 同现状 | 同现状 |

安排单存在与否以服务端为准，**优先于**本地「回过前台」标记 —— 关页重进、杀进程重启都能回到 B3。

### 1.2 安排单字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `plannedStartTime` / `plannedEndTime` | 时间 | 否 | 不填 = 按原约；改时默认保持原时长 |
| `startAddress` + `startLatitude` / `startLongitude` | 高德 POI | 否 | 不填 = 按原约；坐标走现有 GCJ-02 单点入口 |
| `meetSpotNote` | 文本 ≤30 字 | 否 | 具体在哪儿见 |
| `volunteerTopColor` | 闭合颜色枚举（开放解码） | 否 | 陪跑员当天上衣颜色 |
| `runnerTopColor` | 闭合颜色枚举（开放解码） | 否 | 陪跑员**在电话里问来的**跑者上衣颜色；跑者不确定就空着 |
| `version` | 整数 | 服务端生成 | 每次提交 +1 |

- 陪跑员一个字段都不改也要提交，提交本身就是他的「合适」。
- 两个文本 / 颜色字段由**陪跑员**写，AGENTS.md §8「盲人自由文本接单后才可见」不适用；但 `IntroCallView` 注释里「不要往这个 DTO 里加自由文本」要改写并说明破例理由。
- `runnerTopColor` 是 Jayden23018/blind-run-backend#363 的另一条解法：由陪跑员问，不要求盲人出门前自填。

### 1.3 端点变化（待后端拍板）

1. **新增** `PUT /api/orders/{id}/intro-call/plan`：仅本轮候选陪跑员；创建或替换安排单，同时代表陪跑员 ACCEPT；`version + 1` 并**清掉盲人之前的确认**；提交时即跑门槛校验（第 5 节）。
2. **改** `POST /intro-call/decision`：盲人 ACCEPT 必须带 `planVersion`，不是最新版本返回 409 `INTRO_CALL_PLAN_STALE`；没有安排单返回 409 `INTRO_CALL_PLAN_REQUIRED`。陪跑员不再用它发 ACCEPT，DECLINE 不变。
3. **改** `GET /intro-call`：两端返回 `plan`，并带原约的时间与地点（客户端据此念「从 X 改为 Y」与地点距离）。
4. **改** `confirmMatch`：成单前用安排单重跑门槛 → 写入订单 → 成单。远期 / 即时分流本来在成单时计算，自然用新时间。
5. **后端重构**：把 `createOrder` 内联的五道门槛抽成可复用方法；盲人时段冲突检查加「排除本单」。

## 2. 陪跑员端

| 屏 | 内容 | 按钮 |
|---|---|---|
| V1 等来电 | 跑者称呼、掩码号、截止时刻 + 剩余分钟、本单信息（时间、出发地、距离、导盲犬、配速）。收到 `INTRO_CALL_INCOMING` 后副标题换成「跑者正在给你打电话」，保持 2 分钟，播报一次 | 主「聊过了，填见面安排」；次「不合适」；文字「一直没接到电话」 |
| V2 填见面安排 | 页头「把电话里说好的写下来，跑者听完确认就算约好。」时间：原约 +「改」（5 分钟一档，最早现在 + 30 分钟 + 窗口剩余，最晚 7 天，时长默认不变，夜间窗口与时长上限就地校验）；地点：原约 +「改」（高德输入提示）；具体在哪儿见（≤30 字，占位「例如：南门保安亭左边」）；你的上衣、跑者说他的上衣（色块单选，含「不确定」）；固定提醒「见面时请你主动走过去，先报自己的姓。」 | 主按钮随改动变化：「按原约，发给跑者确认」/「发给跑者确认（改了时间、地点）」 |
| V3 等跑者确认 | 「已发给跑者，等他确认」；倒计时；安排单摘要，改过的项标「已改」。**不显示**跑者是否在听、是否同意 | 次「修改安排」（重提交前提示「改了之后跑者要重新确认」）；文字「不合适」 |
| V4 结局 | 约好：原地变订单页「约好」，新增显示见面点、双方上衣颜色。没约成：沿用 v6 中性文案，**加「回首页」按钮，不自动跳转** | — |

播报：提交成功「已发给跑者确认」；来电提醒「跑者正在给你打电话」；约好「已约好」并接着念见面点。

文案只说「正在给你打电话」，不说「通话中」—— 后端只知道盲人按了拨号，不知道接通没有。

## 3. 盲人端

| 屏 | 内容 | 按钮 |
|---|---|---|
| B1 待通话 | 沿用 v6：「李\*想陪你跑」+ 剩余分钟 | 主「打电话给李\*」；次「换一位」；底栏「求助与安全」；导航栏「重复当前状态」 |
| B2 等安排 | 进入条件：App 从**后台**回到前台且安排单未到。「等李\*发来见面安排」；「他会把电话里说好的时间、地点写下来发给你。你听完点确认，就算约好。」**v6 的「聊过了，合适」去掉** | 次「再打一次」「换一位」 |
| B3 听安排、做确认 | 焦点落到标题，念「李\*发来了见面安排，改了 2 项。」下面每项一个读屏元素，**顺序固定**：开跑时间 → 集合地点 → 具体在哪儿见 → 李\*今天穿 → 李\*记下你穿 → 固定句「见面时他会走过来，先报自己的姓。」改过的项开头念「改了」并给新旧值，地点另念离原地点多远 | 「对，就这样」与「不对，再打电话说」**同样大小**；文字「换一位」 |

- B3 示例朗读：「开跑时间，改了：从明天 7:00 改为 7:30，到 8:30 结束」「集合地点，改了：从朝阳公园南门改为东门，离原来的地方约 800 米」。
- 「不对，再打电话说」直接拨号，安排单保留；陪跑员端只会收到又一次「跑者正在给你打电话」，不暴露「跑者不同意」。
- 盲人在 B3 时陪跑员改了安排，或点「对」时收到 409 `INTRO_CALL_PLAN_STALE`：重新落焦标题，念「李\*改了安排，请再听一遍」，不当错误处理。
- 「重复当前状态」在 B3 重念整张安排单。
- 约好后订单页播报：「约好了。明天 7:30，朝阳公园南门，南门保安亭左边。李\*穿红色上衣，见面时他会先报姓。」
- ⚠️ 「先报总数，再逐项，改过的项念新旧值」没有针对读屏用户的研究支撑，是推断，**需找盲人用户真机试**。

## 4. 四段等待

| 等待 | 系统知道什么 | 盲人端 | 陪跑员端 |
|---|---|---|---|
| 通话中 | 盲人按了拨号（`notify-incoming`）；App 回到前台 | 系统电话；回来进 B2 | V1「跑者正在给你打电话」2 分钟 |
| 一方表态等另一方 | 安排单有无 | B2 | V3 |
| 填表后等盲人确认 | 安排单版本、盲人是否确认 | B3；安排单发出 10 分钟仍未确认、窗口未到期时**提醒一次**（播报 + 本地通知）「李\*发来的见面安排还没确认」 | V3，不提醒、不显示跑者状态 |
| 窗口快到点 / 已超时 | `windowEndsAt` | 见下 | 见下 |

- **不扩大 `CXCallObserver` 用途**（现仅用于通话中暂停播报，`blindRun/Voice/AnnouncementQueue.swift:150`）：拿不到号码、后台收不到回调、大陆审核态度不明。
- 「回到前台」只认 `(.background → .active)`；`(.inactive → .active)`（拨号确认框取消、权限弹窗）一律忽略。
- `notify-incoming` 客户端节流：每 60 秒最多一次。
- 倒计时：两端一个常驻读屏元素，标签「通话确认还剩」，按分钟静默更新（`updatesFrequently`）；只在**剩 5 分钟**、**剩 1 分钟**各主动播报一次，内容按子状态说下一步（如 B3：「还剩 5 分钟，听完安排请点确认」）；不足 1 分钟显示「不到 1 分钟」，不消失。
- 超时：盲人在 B3 时先念「这次安排没有生效」，再念现有「正在为你寻找合适的陪跑伙伴」；陪跑员端为 V4 中性文案。
- **不做窗口延长**：窗口期间候选人锁单，其他志愿者接不了，属 WCAG 2.2.1 的「必需时限」。真机试用后若不够用，请后端调大 `app.intro-call.window-minutes`。

## 5. 异常、校验与安全

1. **提交时校验**（`PUT /plan`）：复用 `APPOINTMENT_TOO_SOON / TOO_FAR / TOO_LONG / IN_NIGHT_WINDOW` 与陪跑员时段冲突。跑者时段冲突**不得**用 `DUPLICATE_ORDER` 文案（会泄露跑者行程），陪跑员端只说「这个时间不行，换一个试试」。
2. **提前量多算一个窗口**：新开跑时间距现在 ≥ 30 分钟 + 窗口剩余时间，保证盲人最晚确认时仍满足 30 分钟。
3. 成单复检仍失败（只剩跑者期间自己又下了冲突单）：同现状，本轮结束，中性文案。
4. 网络失败：盲人点「对」失败留在 B3，**屏幕显示**并播报「没有发出去，请再点一次」；陪跑员提交失败保留表单，顶部显示错误。陪跑员轮询的网络错误依赖 #428。
5. 颜色是开放解码：不认识的值那一行不念，整张单不崩。
6. **安全（改集合点被滥用）**：威胁模型是「陪跑员可能就是威胁来源」，改集合点 = 陌生人能指挥盲人去哪。三层缓解：朗读离原地点多远；后端距离上限 **3 公里**（负责人 2026-10-15 拍板）；安排单每个版本留历史供客服查。成单后行程分享自动带上新地点。
7. **隐私**：没约成，安排单随本轮删除；约好后时间地点写进订单，见面点与颜色在订单结束后 N 天删除（**N 待负责人定**，《个人信息保护法》第十九条只要求「必要的最短时间」）。
8. 实现时触及新端点 + 用户输入 + 地点变更，**必须叫 security-reviewer**。

## 6. v6（PR #400）审视意见

1. **颜色太多**：每个状态一种头卡色，通话步骤再加紫、梅红两种，跑步中另有一套。与 `docs/ui/design-direction.md`「不新增强调色」冲突。视觉另议；倾向通话沿用进度绳上「匹配」那一步的颜色。
2. 盲人「聊过了，合适」去掉，换 B2 / B3。
3. 陪跑员「已说合适，等确认」换 V2 / V3。
4. 陪跑员没约成停 3 秒自动回首页：可能截断播报，改为保留文案 + 「回首页」按钮。
5. 审查第 6 节列出的行为漏洞 v6 都还在（只换了外观）；除 #428 外均由本设计覆盖。
6. v6 尚未真机跑过任何测试。

## 7. 测试计划（实现阶段）

- 单测：子状态推导（无单 / 有单 / 版本变化 / 已确认）；朗读文本（只有改过的项带新旧值、地点念距离、未知颜色跳过）；回前台判据（**必须喂 `(.inactive → .active)` 并断言不触发**）；倒计时 5 / 1 分钟各响一次且轮询不重复；409 `INTRO_CALL_PLAN_STALE` 走「再听一遍」；陪跑员主按钮文案随改动变化；提前量含窗口剩余。
- 真机 UI：B3 焦点落标题；三个按钮滚动后断言高度 ≥ 64pt；底部求助条不被遮挡。
- 后端：新版本清掉盲人确认；成单写入安排单；距离上限；冲突检查排除本单；提前量含窗口。
