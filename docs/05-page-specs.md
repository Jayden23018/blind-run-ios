# 05 — 页面规格

> 共 16 个页面。每个页面按 8 个维度描述：页面目标、入口、主要内容、主要操作、状态变化、错误状态、空状态、无障碍要求。

## 页面 1：登录页（手机号 + 验证码）

**页面目标**：用户通过手机号 + 验证码登录，首次登录自动创建账号。

**入口**：App 启动（无有效 token 时）。

**主要内容**：
- App Logo / 名称"助盲跑"
- 手机号输入框（11 位数字键盘，placeholder: "请输入手机号"）
- "获取验证码"按钮（手机号格式正确后启用）
- 验证码输入框（6 位，placeholder: "请输入验证码"）
- 验证码倒计时（60 秒，"重新发送"链接）
- 环境切换入口（底部或角落，不显眼：Mock / 本地 / 生产）

**主要操作**：
- 输入手机号 → 点击"获取验证码"
- 输入验证码 → 自动验证（6 位填完后自动提交，或手动点击"登录"）
- 点击"重新发送"（倒计时结束后显示）
- 点击环境切换

**状态变化**：
- 手机号格式校验中 → 实时提示格式错误
- "获取验证码"点击 → 页面提示"验证码已发送"，按钮变为倒计时（60 秒）
- 验证码输入 → 调用 `POST /api/auth/verify-code` 并跳转
- 首次登录 → 角色选择页
- 非首次登录 → 直接进入上次选择的角色首页

**错误状态**：
- 手机号格式错误 → 红框 + "请输入正确的手机号"
- 验证码错误 → 抖动 + "验证码错误，请重新输入"
- 网络错误 → Toast "网络错误，请重试"

**空状态**：无（登录页必然有输入框和按钮）。

**无障碍要求**：
- 手机号输入框：accessibilityLabel = "请输入11位手机号"
- 验证码输入框：accessibilityLabel = "请输入6位验证码"
- "获取验证码"按钮：accessibilityHint = "点击后发送验证码"
- TTS：进入页面不自动播报（避免打扰）

## 页面 2：角色选择页

**页面目标**：用户选择本次使用的角色（盲人跑者 / 志愿者）。

**入口**：首次登录验证码验证成功后。
（~~用户从设置主动切换角色~~ —— **【未决 / 未实现】入口已删除**：后端没有角色切换端点，设置页的切换角色入口已从 App 中移除。见 `docs/04-user-flows-and-state-machine.md` 第 6 节。）

**主要内容**：
- 标题："请选择您的角色"
- 两个大型卡片：
  - 盲人跑者卡片：图标、标题"我是盲人跑者"、副标题"预约志愿者陪我跑步"
  - 志愿者卡片：图标、标题"我是志愿者"、副标题"陪伴盲人跑者完成跑步"
- 底部提示："一个手机号可同时拥有两个身份，后续可在设置中切换"

**主要操作**：
- 点击"盲人跑者"卡片 → 进入盲人资料页（首次）或盲人首页
- 点击"志愿者"卡片 → 进入志愿者认证页（首次）或志愿者首页

**状态变化**：
- 选择后保存 activeRole 到后端和本地
- 如果有角色对应的活跃订单（PENDING_ACCEPT / DRIVER_EN_ROUTE / DRIVER_ARRIVED / IN_PROGRESS），先弹窗拦截再决定

**错误状态**：
- 网络错误 → Toast "网络错误，请重试"
- 角色保存失败 → Toast "角色设置失败"

**空状态**：无。

**无障碍要求**：
- 每个角色卡片是单个 VoiceOver 元素，包含标题和副标题
- 盲人跑者卡片：accessibilityLabel = "我是盲人跑者，预约志愿者陪我跑步"
- 志愿者卡片：accessibilityLabel = "我是志愿者，陪伴盲人跑者完成跑步"

## 页面 3：盲人资料页

**页面目标**：盲人跑者填写个人资料，完成注册。紧急联系人已从本页拆出，由「页面 3b：紧急联系人管理页」维护。

**入口**：角色选择页选择"盲人跑者"（首次）/ 设置页 → 编辑资料。

**主要内容**：
- 标题："完善信息"
- 昵称输入框（必填）
- 跑步经验选择器（选填：无经验 / 偶尔跑 / 经常跑）
- 实名认证入口与状态（**下单硬门槛**，未通过时无法创建预约；状态取自 `BlindProfileResponse.verifyStatus`，仅 `NOT_VERIFIED` / `VERIFIED` / `FAILED` 三态，不存在「审核中」）
- "完成"按钮

**主要操作**：
- 填写所有必填项 → 点击"完成" → 保存到后端 → 首次注册继续引导至紧急联系人管理页，再进入盲人首页
- 选填跑步经验
- 已有资料时：预填已有数据

**状态变化**：
- 提交 → loading → 成功（跳转首页）
- 编辑模式（来自设置）：标题变为"编辑资料"，按钮文字变为"保存"

**错误状态**：
- 必填项为空 → 按钮禁用 + 空字段红框标记
- 手机号格式错误 → "请输入正确的手机号"
- 网络错误 → "保存失败，请重试"

**空状态**：无（首次使用时字段为空）。

**无障碍要求**：
- 每个输入框有清晰的 accessibilityLabel
- 必填字段标记为 accessibilityHint = "必填"
- 完成按钮：最小高度 64pt
- TTS：进入页面播报"请填写个人资料"

## 页面 3b：紧急联系人管理页

**页面目标**：维护 1～5 个紧急联系人，并保证恰好 1 个主联系人。**这是盲人下单的硬前置条件**。

**入口**：盲人资料页完成后（首次注册）/ 设置页 → 紧急联系人 / 创建预约被阻断时的跳转入口。

**主要内容**：
- 标题："紧急联系人"
- 联系人列表（每行：姓名、关系（选填）、脱敏电话、是否主联系人）
- "添加联系人"按钮（已有 5 个时禁用）
- 每行操作："编辑"、"设为主联系人"（非主联系人才显示）、"删除"

**新增 / 编辑表单**：
- 姓名输入框（新增必填）
- 电话输入框（新增必填，11 位数字键盘）
- 关系输入框（选填）
- 编辑时电话默认以脱敏形式展示；未修改则不提交该字段，服务端保留原值（后端 PUT 为 PATCH 语义）

**主要操作**：
- 新增 → `POST /api/users/{userId}/emergency-contacts` → 刷新完整列表
- 编辑 → `PUT /api/users/{userId}/emergency-contacts/{contactId}` → 刷新完整列表
- 删除 → `DELETE /api/users/{userId}/emergency-contacts/{contactId}` → 二次确认 → 刷新完整列表
- 设为主联系人 → `PUT /api/users/{userId}/emergency-contacts/{contactId}/set-primary` → 刷新完整列表

**状态变化**：
- 首个联系人由后端自动设为主联系人
- 设为主联系人为原子操作，原主联系人自动取消

**错误状态**：
- 已有 5 个 → 新增入口禁用，提示并播报"最多添加 5 个紧急联系人"
- 只剩 1 个时删除 → 阻止，提示"至少保留 1 个紧急联系人"
- 尝试删除主联系人（存在其他联系人时）→ 要求先把另一个设为主联系人
- 手机号格式错误 → "请输入正确的手机号"
- 网络错误 → "保存失败，请重试"

**空状态**：无联系人时展示"还没有紧急联系人，添加后才能创建预约"，并突出"添加联系人"。

**无障碍要求**：
- 每行是单个 VoiceOver 元素，依次播报姓名、关系（有则播）、脱敏电话、是否主联系人、可用操作
- 删除为破坏性操作，必须二次确认
- 主按钮最小高度 64pt
- 增删改和设为主联系人成功后播报结果与当前联系人数量 / 主联系人
- 播报和 accessibility 值只使用脱敏电话，不读出完整号码

**状态变化**：
- 无订单 → 有订单：UI 从"开始约跑"切换为订单卡片
- 有订单 → 无订单：UI 恢复"开始约跑"；REMATCHING 取消成功后也返回无活跃订单状态
- 与当前订单关联且 `fromStatus` / `toStatus` 均合法的 `ORDER_STATUS_CHANGED` 先更新内存中的订单状态并立即播报，再在后台刷新完整详情；错误订单、非法状态、重复事件和与当前状态不一致的迟到事件只触发安全刷新，不直接覆盖页面
- 相同合法 `messageId` 与状态指纹的重连重发不得再次更新页面、播报或触发 REST；UUID 身份碰撞只允许一次有界安全刷新。生命周期 `APP_NOTIFICATION` 与结构化状态事件并行到达时只保留客户端固定状态文案的一次播报
- 首页与订单详情共享同一订单状态协调结果；WebSocket 已推进到 `DRIVER_EN_ROUTE` 后，较早发起的 REST 请求即使返回 `PENDING_ACCEPT` 也不得回退页面、播报或同行会话
- 状态更新完成后，定位会话、位置发送与完整详情刷新分别在后续执行周期调度；任一副作用永久悬挂都不得阻塞当前状态、滚动或"重复当前状态"（~~地图 marker~~ 首页装饰地图已删除）
- 页面生命周期、WebSocket 重连、定时和手动刷新同时触发时，合并为同一项首页请求；重复触发不得取消重启请求或推迟原 20 秒截止
- ~~Debug、DemoRelease 和 Production 均直接挂载一张辅助高德地图；角色根路由离开时随首页卸载，不使用发布占位开关~~ **首页不再挂载任何地图**（2026-09-16）。装饰地图仍在订单状态页

**错误状态**：
- 定位失败 → 明确显示"使用演示坐标"或"正在获取设备定位"，不得暗示已获得真实会合点
- 网络请求加载、超时或失败不得阻断首页滚动、底部标签栏或"重复当前状态"；~~设置、位置摘要或辅助地图~~ 那三样已不在首页。**订单状态未确认前只阻止创建重复预约** —— 判据是加载有没有落定，**不是「有没有活跃订单」**：后端允许同时握着多张未走完的单（`DUPLICATE_ORDER` 只拦时段冲突，上限由 `TOO_MANY_SCHEDULED_ORDERS` 管，默认 3），拿「有订单」当闸会让预约块在有订单时变成一个按不动、且解释错误的入口
- 首页请求超过 20 秒 → 结束加载提示，显示明确错误和可点击的"重试加载"；迟到响应不得覆盖较新的请求状态
- AMap Key 缺失或地图初始化失败 → 显示地图配置故障提示，但首页其余内容和操作保持可用

## 页面 5：创建预约页

**页面目标**：盲人跑者创建跑步预约订单。

**入口**：盲人首页 → 点击「预约新的陪跑」。

**前置条件**：角色为 `BLIND`、盲人资料完整、**已保存 1～5 个紧急联系人且恰好 1 个为主联系人**、定位权限已授予、已确认出发地点、预约时间至少在 30 分钟后。实名认证状态不属于前置条件，只作引导性提示。

**语音下单：一次说完 → 读回整单 → 确认或定点修改**
- 第 1 轮请用户用一整句说完三项："请说你想从哪儿出发、什么时候跑、跑多久，比如：明天早上八点从人民广场出发跑一个小时。"
- 这一句发**一个**请求（`POST /api/orders/voice/parse`，2026-08-04 起）同时抽起点、开始时间、时长。**这一轮不重问、不失败**：抽出多少算多少，抽不出的保留默认值（起点默认当前位置、时间默认最早可约时间）。把用户按在同一句话上反复喊，正是这里要避免的
- 第 2 轮读回整单，三段缺一不可：**先念用户原话**（否则分不清是自己说错还是系统听错）+ **再念最终要下的单**（否则不知道默认值补了什么）+ **最后给出出路**（看不见屏幕的人不会自己发现还能说"改时间"）
- 时长**说多少就是多少**，只在超出契约区间（10～300 分钟）时夹到边界，且夹了就**必须说出来**："你说的是 400 分钟，超出了可预约范围，本次按 5 小时预约。" 静默改动对听不见屏幕的人就是篡改。（就近 snap 到 6 个枚举档位已于 2026-08-06 删除 —— 枚举存在的理由是选择器需要有限选项，而说话的人不需要选择器）
- **结束地点是可选的第四项**（2026-08-09，后端 SPEC A/B1）：说了「跑到五角场」才有，没说就没有。读回时**紧跟出发地点念**，因为起终点由大模型抽取、抽反了只有读回能被发现，而两句挨着才听得出来。没说终点时一个字都不提（空 ≠ 原路返回起点）。说了地名但高德查不到坐标时照样带地名下单，并说清「这个地点没能定位到，志愿者会看到这个名字」。**表单没有终点输入框** —— 它是可选槽位，为它再加一段 POI 搜索是与起点等长的第二段交互
- **出发地撞了同名地点时，先让用户挑一个再读回**（2026-08-10，接后端 `candidates`，N48）：
  - 后端在**请求带了坐标**时用高德 POI 周边搜索 + 拼音重排取前 3 个，≥2 条即返回 `candidates`。念的是**后端的 `ttsText`**（「找到3个地点，请说第几个。第一个，五角场，杨浦区，距您800米。」）—— 名称、行政区、距离只有后端知道，客户端拼不出来
  - **必须排在读回之前**：读回念的是「我们的最佳猜测」（候选第一条），用户听完多半就说「确认」，那批候选白算了，而如果第一条不是他要的，错地点已经被确认下单 —— 而读回念得很顺，他无从分辨
  - 用户说「第二个」，序数**在本地判**（汉字与阿拉伯数字两种写法都认，`count` 是护栏：只念了 2 个不认「第三个」）
  - ⚠️ **这一轮的回答不发回 `/parse`**：「第二个」不是地名，模型会把它圈成起点 span，高德查不到又按后端口径保留下来，于是把刚挑好的地址冲掉。消歧闭环整个留在客户端
  - 挑完**同时换掉回传的槽位快照**，否则确认轮把旧 `current` 发回去，后端按旧快照继承成第一条，用户刚挑的那一下白挑且没有任何提示
  - 三次挑不出来**不丢回表单**（手上已有可用的最佳猜测，读回会念出来、仍可说「重说」），但**必须说出「没听清是第几个，先按第一个来」** —— 静默取第一条正是这批改动要消灭的那个失败
  - **上限只有 3 个**（后端截断，不是客户端展示限制）：纯听觉且要同时理解句子时，人平均只能记住约 3 项
  - **终点永远没有候选**：一次播起点 3 项 + 终点 3 项超过上面那条上限。终点抽错走读回 + 「终点错了」
- **读回之后不是「确认 or 整句重说」二选一**（2026-08-10，接后端 `current` / `userIntent` / `correctionTarget`）。用户可以：
  - **直接说要改的那一项**："把时间改成明天早上九点" → 只有时间变，起点/终点/时长/可选槽位一个都不丢，改完回到读回把整单再念一遍
  - **只点名不给值**："我想改一下终点" → 播后端的定向追问语（"好的，请说新的结束地点"），再收一次音，下一句只说值就回到读回。**不换步骤、不换屏**
  - **只说"不对"** → 播消歧问句"您想改哪一项？"
  - **要求重听 / 取消 / 整句重说** → 各自到位
- 实现是**两档**：命中本地 27 个整串词（确认 / 重说 / 重听三组）→ 零延迟直通不发网络；其余一律发 `POST /api/orders/voice/parse` 并**带上上一轮的槽位快照 `current`**，由后端分意图
  - 本地表**不撤**（后端建议撤过）：后端的确定性兜底跑在服务端，挡不住网络。一次确认往返 3.4~4.3 秒、超时 12 秒，让最高频的那句"确认"等 4 秒、网络一抖就下不了单，等于把一次已经解析成功的语音下单在最后一步丢掉
  - 本地表必须是后端 `VoiceSlotParser` 那 5 条 `INTENT_*` 正则的**子集**，由 `scripts/validate-voice-intent-words.mjs` 逐词对撞钉住。肯定词仍只整串匹配（"不确认""确认一下时间"都含"确认"但意思相反）
  - 快照**只从上一次响应派生，绝不从表单 view model 派生** —— `appointmentTime` 的初值是 `Date()`，从它取会把一个用户从没说过的时刻当成"已确认槽位"发出去
- ~~⚠️ 已知缺口：整句里说了地点但后端抽不出时，会静默落回当前位置~~ **已修（2026-08-10，N48）**：接了 `addressUnresolved`，听见了地名却没查到时，读回**前**先说一句「没找到你说的那个地点，出发地先按当前位置来，要改就说『重说』」，且与时长夹取提示**一起说**而不是二选一。措辞上说的是「没找到」不是「没听到」—— 我们听到了，是查不到
  - ⚠️ 这个 `true` 从 2026-08-10 起会**变常见**：后端同批不再拿全国范围的正向编码兜底（那条路曾把深圳说的地名解析到海南），改成诚实认输。**代价是约 50 公里外的地点会解析不出、被追问**，收益是不会把人约到另一个省
- **语音开始时主动要一次定位**（2026-08-10，N48 的根因第一环）：`onAppear` 的持续定位在非陪跑模式下 `distanceFilter = 10`，**站着不动 Core Location 不推新样本**，而语音下单恰恰是站着说完一整句（10~20 秒）。不主动要一次新 fix，请求就不带坐标 —— 而**没有坐标后端连候选都给不出来**，只能拿地名做全国范围解析。兜底是把语音这一处的样本新鲜度门放宽到 300 秒（**只这一处**，紧急求助等另外三个调用点各有各的要求）

**页面形态：语音态与表单态二选一，绝不同屏共存**（2026-08-08）
- 语音在跑时，内容区**只有一块状态区**（占满内容区，读回轮下面再加一张整单），底栏是「重复一遍」「改用表单」两个全宽竖排按钮。**四步表单、地点搜索框、补充描述框、辅助地图一个都不渲染。**
  - 状态区对 VoiceOver 是**一个**焦点：label 说现在能做什么（正在录音 / 双击跳过播报 / 正在识别），value 是系统刚念的那句话
  - 解析途中状态区仍在（否则那几秒屏幕上没有任何东西说「正在识别」），但不暴露可激活动作
  - 读回轮那张整单一行「一个名字 + 一个值」，不写「出发地点：」这类前缀；**时间只在真的抽到时才显示具体时刻**，抽不到就写「还没说」；**结束地点只在说了时才有那一行**（查不到坐标的标「（未定位到）」）
- **读回念的地址与下单带的地址不是同一个串**（2026-08-12 接入后端 `addressShort` / `endAddressShort`）：
  - **念**的是 POI 名（`五角场市场监督管理所`）。读回存在的唯一意义是让用户听出「这不是我说的地方」，
    而他能靠听分辨的是**名字**；`国定路335号1号楼4层(国权路地铁站4号口步行110米)` 听完无从判断，
    只会把确认句拖长、把关键信息埋掉
  - **下单与屏幕显示**仍是完整地址，一个字不少 —— 志愿者要靠门牌号找到人
  - 后端没给短名（老版本、或正向地理编码回落给的 `上海市黄浦区人民广场` 本来就没有 POI 名分隔）时
    退回完整地址：念长一点总好过整项不念
  - 候选消歧挑定之后念**他挑的那个**候选的 `name`，不是上一轮最佳猜测的名字
  - 手动从表单搜索改了起点，短名立即作废 —— 否则屏幕上显示 A、耳朵里听到 B，
    而看不见屏幕的人只有耳朵那一路
- 停语音（按「改用表单」）或语音降级时，整页换成表单态，并**停在向导刚念过的那一步**（确认步）
- 表单**不移出本页**：它既是降级出路也是隐私出路（在公共场合不愿说出自己的位置时的唯一替代路径）
- 语音**自己放弃**后（不是用户主动切换），若前置门槛全通过，表单顶部给一条**零输入下单**路径：用当前位置 + 最早可约时间成单，两步 —— 第一步念整单，第二步按钮的标题即整单（含绝对时刻，不说「最早可约时间」），旁边留「不用了，我自己填」

**主要内容（表单态）**：
- 引导步骤 1：确认出发地点
  - 当前出发地点文本摘要先于地图展示
  - 可保留默认当前位置，也可通过高德 POI 搜索选择地点
  - 搜索输入框 + 麦克风按钮（语音输入）
  - POI 搜索结果列表（显示地点名称和地址，不显示原始经纬度）
  - 辅助高德地图位于文字摘要、搜索和结果之后，只用于视觉确认
- 引导步骤 2：预约时间选择（DatePicker，不早于当前时间 + 30 分钟）
- 引导步骤 3：跑步需求（全部选填）
  - 路线备注输入框（带麦克风按钮）
  - 预计跑步时长选择（15 分钟 / 30 分钟 / 45 分钟 / 1 小时 / 1.5 小时 / 2 小时 / 不填写）
  - 配速偏好选择（走跑结合 / 轻松 / 中等 / 快速 / 无偏好）
  - 路线偏好选择（公园步道 / 街道 / 跑道 / 无偏好）
  - 本次携带导盲犬开关
  - 特殊说明输入框（选填，多行文本，带麦克风按钮）
- 引导步骤 4：确认并提交
  - 汇总出发地点、预约时间和已填写的选填需求
  - 未填写的选填字段不显示在确认摘要或复述语音中
  - "提交预约"按钮（最小高度 64pt）

**主要操作**：
- 每一步点击"下一步"进入后续步骤；不满足必填条件时显示并播报阻塞原因
- 点击"重复当前状态" → 播报当前步骤、当前值、下一步动作和阻塞错误
- 点击"提交预约" → 创建订单 → 订单状态等待页

**状态变化**：
- 定位初始化 → 自动填充当前位置
- 地点搜索 → 显示 POI 结果列表；语音识别结束且识别文本非空时自动搜索
- 步骤切换 → 只播报新步骤摘要，不在每次输入或 DatePicker 调整时自动长播报
- 提交 → loading → 成功跳转 / 失败提示

**错误状态**：
- 缺少紧急联系人或没有恰好 1 个主联系人 → 阻止提交，"请先添加紧急联系人并设置主联系人" + 跳转紧急联系人管理页入口

- 定位失败 → 使用默认测试坐标时明确标注"演示坐标"，不得暗示是真实出发点
- 预约时间不足 30 分钟 → "预约时间需至少在 30 分钟后"
- 出发地点为空 → "请选择出发地点"
- 网络错误 → "提交失败，请重试"

多个前置条件同时缺失时，只展示并播报**第一个可执行的**缺失项；"重复当前状态"必须包含该阻断原因。

**空状态**：
- POI 搜索结果为空 → "未搜索到相关地点"

**无障碍要求**：
- 出发地点搜索框：accessibilityLabel = "搜索出发地点"
- 麦克风按钮：accessibilityLabel = "语音输入出发地点"
- 语音识别中：搜索按钮显示并播报"语音识别中"，识别成功后自动搜索地点
- 搜索结果：VoiceOver 播报结果数量和第一个地点名称，结果项读出地点名称和地址
- 时间选择器：使用系统 DatePicker，可被 VoiceOver 访问
- 辅助地图：accessibilityLabel 必须说明"辅助位置确认"，不得朗读原始经纬度
- 下一步 / 提交按钮：最小高度 64pt
- TTS：进入页面不自动播报，提交成功后播报"订单提交成功"

## 页面 6：盲人订单状态等待页

**页面目标**：展示订单当前状态，等待系统派单、志愿者接单和到达。

**主要内容**：

**状态卡恒定只给一个数字**（`RunOrderStatus.offersWaitedDuration` / `offersVolunteerDistanceToStart` /

| 状态 | 那个数字 | 来源 |
|---|---|---|
| PENDING_MATCH / REMATCHING | "已等待 X 分钟" / "已等待 X 小时" | `createdAt`（下单时刻）到当前时间 |
| PENDING_ACCEPT / DRIVER_EN_ROUTE / DRIVER_ARRIVED | "志愿者距出发地点约 X" | 志愿者最新位置到订单出发坐标 |

- "已等待"的锚点是**下单时刻**，不是本轮匹配开始时刻——后者（`lastRematchAt`）不在订单详情契约里。
- **不得据此推算"还能等多久"**：放弃时刻是 `plannedStart` 减去后端配置且被"继续等待"往后推

  与"继续等待"成功文案同一条口径。
- 上下界：不足 1 分钟不显示（"已等待 0 分钟"是噪音），满 1 小时后按整小时说，
  超过 24 小时整格消失（提前很久下的单在派单期确实等了那么久，但"已等待 168 小时"吓人且不可行动）。

**滚动区顺序**（顺序即优先级，看不见屏幕的人靠遍历顺序发现功能存在）：

**空状态**：不适用（订单已创建）。

**无障碍要求**：
- 状态文本：大号字体，高对比度

- 本页覆盖的状态均不显示"一键求助"或"紧急求助"按钮

  焦点自动落回该卡，所以读屏用户听得到；低视力用户靠卡上那行大字看到——两条通道都有

  > ⚠️ **PENDING_MATCH 反过来：一个字都不许提。** 那个按钮已删（见上文"继续等待"那条），

  > `KeepWaitingTests.testRepeatStatusMentionsKeepWaitingWhileWaiting`（REMATCHING 要念）
  > 与 `...StaysSilentAboutKeepWaitingWhilePendingMatch`（PENDING_MATCH 不许念）。

## 页面 7：盲人服务中页

**页面目标**：在服务进行中显示相关信息，并提供盲人一键求助入口。

**入口**：订单状态变为 IN_PROGRESS 后自动跳转 / 盲人首页点击进行中订单。

**主要内容**：
- 页面标题："服务进行中"

- "重复当前状态"按钮

**底部常驻条的构成（`safeAreaInset(edge: .bottom)`，恒为两个版位）**：

> 🔄 **2026-09-16 起本表只管订单页 / 服务中页，不再管首页。** 首页已改成标签栏结构，
> 底部那条固定条是标签栏本身；「重复当前状态」按项目负责人拍板移入求助与安全中心弹层。
> 「恒为两个版位」与「不要加第三个版位」这两条对**本页**仍然成立。

| 版位 | IN_PROGRESS | 其余状态 |
|---|---|---|
| 上 | 求助区块（一键求助 + 结果文案 + 撤销求助） | "问一句" |
| 下 | "重复当前状态" | "重复当前状态" |

- IN_PROGRESS 时"问一句"下沉到滚动区、紧跟"打电话给志愿者"，**仍在首屏内**；标识符
  `blindOrderStatusAskQuestionButton` 不变。它是让位不是删除。
- **不得把求助改回滚动区**：它此前排在滚动内容第 7 位，上面压着状态卡、140pt 拨号按钮、
  行程分享与 180pt 装饰地图，实测落在首屏之外 —— 看不见屏幕的人在跑步中要先滑一段才摸得到求助，
  且拿不到志愿者位置时地图退化成一行文字、位置又会变回来。由
  `AccessibilityAuditTests.testBlindOrderStatusKeepsEmergencyReachableWithoutScrolling` 钉住。
- **也不要往这条常驻区加第三个版位**：三个 64pt 按钮在 6.1" 上吃掉约 26% 屏幕，
  治了求助够不着换来别的都够不着。要加之前先想清楚多的那一行值不值得把求助顶下去。
- **背景恒为实色（`AppColors.background`）+ 顶部一条 1pt 不透明分隔线**，不用 `.regularMaterial`。
  分隔线**不要调透明度**：底栏背景与页面背景同色，它是唯一的边界，而 25% 透明度下
  只有约 1.4:1，够不到 WCAG 1.4.11 对控件边界要求的 3:1。
  「问一句」按钮同时补一圈 `AppColors.primary` 描边 —— `secondaryBackground` 压
  `background` 只有 1.06:1（暗色 1.22:1），不描边的话按钮形状在实色底栏上会消失。
  原来只在系统「降低透明度」打开时才实色，默认走材质，于是滚动时正文从按钮底下透上来
  （2026-09-07 真机报的「穿模」）。材质在登录页那种短底栏上没问题，这一页压着长列表，
  透上来的是正文，成了文字叠文字 —— 打掉的正是低视力用户唯一的通道，
  而对比度审计查不出来（它查静态配色，不查两层内容叠在一起）。

**主要操作**：
- 点击志愿者电话 → 系统拨号
- 点击"一键求助" → 二次确认："是否确认进入求助状态？确认后，本次服务将标记为异常，系统会记录当前订单状态。" → 选择"确认求助"提交，选择"取消"什么都不发送
- 点击"重复当前状态" → TTS 播报

**状态变化**：
- 每 5 秒轮询

**空状态**：不适用。

**无障碍要求**：

- "一键求助"按钮：最小高度 64pt，accessibilityLabel = "一键求助，遇到紧急情况时点击"，accessibilityHint 说明需要二次确认并会上报当前位置；每次求助状态变化都同时更新可见文案和 TTS；**位于底部常驻条，不滚动即可达**（见上文"底部常驻条的构成"）

- "重复当前状态"按钮：accessibilityLabel = "重复当前状态"；先播报订单状态，再追加最新求助状态，不替代订单状态

- 动作活体认证 init 返回 PENDING 和非空 certifyId：iOS 向原生 SDK 传入 certifyId 和当前 ViewController，用户按 SDK 页面提示完成动作后前端轮询 result；原生流程不要求 certifyUrl
- 活体认证通过：后端原子设置 currentStep = STEP_4_COMPLETED、canAcceptOrders = true；新注册不得进入 STEP_4_TRAINING
- 活体 result 已通过但 status 尚未完成：显示“活体已通过，注册状态同步中，无需课程或答题”，每 5 秒轮询并提供手动刷新，不允许重复发起活体认证
- status 返回 STEP_4_COMPLETED、遗留 STEP_4_TRAINING 或 canAcceptOrders = true：显示并播报“注册完成，请返回首页开启可服务状态”
- STEP_4_TRAINING 仅用于旧账号或尚未升级后端的兼容；iOS 将其按主注册完成处理并停止轮询，但不会自动开启可服务状态
- 可选资质证书上传使用 `POST /api/volunteer/verification`（multipart），不属于主注册引导链路，不影响接单资格。约束：单文件 ≤ 5 MB；扩展名白名单 `.jpg` / `.jpeg` / `.png` / `.gif` / `.webp` / `.bmp` / `.pdf`，后端同时校验文件魔数，扩展名与内容必须一致。**白名单没有 `.heic`**，相册里的 HEIC 必须由 iOS 先转成 JPEG 再上传，否则一定 400。状态查询 `GET /api/volunteer/verification/status` → `{"status":"NONE|PENDING|APPROVED|REJECTED"}`；状态查询失败时不猜测状态、也不允许盲传
- 可服务开关由志愿者首页单独控制，认证不自动开启 isAvailable / wantsDispatch
- 提交：loading → 成功跳转

**错误状态**：
- 昵称为空 → "请填写昵称"
- 未完成主注册流程 → "请先完成志愿者注册流程"
- 身份证二要素失败 → 显示后端失败原因并允许重新提交 Step1
- 活体认证发起时返回身份信息错误 → 允许返回 Step1 修改姓名和身份证号码后重新提交
- 原生 SDK 用户取消 → 留在活体认证步骤，清除本次 certifyId 并允许重新发起
- 原生 SDK 系统、网络或设备时间错误 → 显示对应原因，清除本次 certifyId 并允许重新发起
- 原生 SDK 返回 1001 → 仅展示根据白名单 subcode 映射的提示和安全错误码；不得展示原始 SDK message、certifyId、metaInfo 或身份字段
- Z1014/Z1023 → SDK 初始化或内部处理失败；I4001 → 刷脸模块接入异常；Z1010/Z1037 → 认证参数或流程配置异常；Z1001/Z1002/Z1020 → 相机不可用；Z1024 → 流程重复发起

**空状态**：无（首次使用时为空字段）。

**为什么删**：

1. **它从来没有入口。** 系统派单（`GET /api/volunteer/dispatch-summary`）上线后，

一个没有入口、拿不到数据、点进去必然失败的页面，留着只会让人以为它能用。

**状态变化**：
- 每 5 秒轮询
- PENDING_ACCEPT → DRIVER_EN_ROUTE（志愿者点击已出发）：UI 更新
- DRIVER_EN_ROUTE → DRIVER_ARRIVED（志愿者点击已到达）：UI 更新

- DRIVER_ARRIVED → IN_PROGRESS（志愿者点击开始服务）：UI 更新；只有进入 IN_PROGRESS 后才显示"结束陪跑"
- IN_PROGRESS → COMPLETED：跳转首页 + 显示"服务完成，感谢你的陪伴"（不报积分数：每单加几分是后端配置，客户端不编数字）

**错误状态**：
- 网络错误 → 保留当前 UI，静默重试
- "我已出发"、"我已到达"、"开始服务"、"结束陪跑"和取消的状态变更 POST 最多等待 12 秒，并与后续详情确认分离；POST 返回后立即释放操作 spinner，不等待 GET 才恢复页面
- POST 成功或传输结果不确定时显示"操作已提交，状态待确认"，禁止重复提交同一状态转换；地图、导航、返回、取消入口和服务信息滚动保持可用
- "我已到达"只能禁用其对应的状态提交按钮；POST 或 20 秒确认查询悬挂时不得禁用服务面板滚动、返回和外部导航，也不得通过地图或同行位置过期刷新维持 spinner
- WebSocket 状态事件或带 20 秒硬截止的详情查询负责确认正式状态；仍未确认时显示"状态确认延迟"和只读"重新确认状态"，不得恢复操作 spinner，也不得重复 POST
- 明确 4xx/5xx 时恢复原状态按钮并允许重试；401 使用现有登录失效流程。迟到响应不得直接覆盖已确认的新状态
- 合法 WebSocket 状态先提交页面、按钮与播报；定位准备、位置发送、地图更新和详情刷新随后独立执行。地图渲染、地图配置故障降级和位置上报不得参与订单按钮或详情确认状态机
- 点击状态按钮时只禁用对应转换操作；ScrollView、返回、外部导航、取消入口和根视图命中始终保持可用
- 结束陪跑失败 → "操作失败，请重试"；若仍处于 DRIVER_ARRIVED，显示"开始服务"按钮并阻止调用 `/api/orders/{id}/finish`。**失败后环形进度必须归零** —— 满格环形是"已经结束了"唯一的视觉读数，而此刻订单还在跑

**空状态**：不适用。

**无障碍要求**：
- "我已到达"按钮：最小高度 64pt，accessibilityLabel = "我已到达约定地点"
- "开始服务"按钮：最小高度 64pt，accessibilityLabel = "开始服务"，accessibilityHint = "点击后通知盲人服务已开始"

- 求助盾牌：64×64pt，accessibilityLabel = "一键求助，遇到紧急情况时点击"（与盲人端**逐字相同** —— 可见文字是圆里的"求助"两字，读屏念出来的必须仍是完整那句），accessibilityHint 说明需要二次确认并会上报当前位置。志愿者端其余触达走 Apple 的 44pt 线（`guard.mjs` 的 `small-touch-target` 显式排除 `/blindRun/Volunteer/`），64pt 是选出来的余量、不是被强制的
- TTS：进入 DRIVER_ARRIVED 状态不自动播报（由盲人端播报）
- TTS：进入 IN_PROGRESS 状态播报"服务已开始"

## 全局前台实时通知层

**页面归属**：位于 `ContentView` 根层级，覆盖盲人/志愿者导航但不归属某个功能页。

**显示规则**：

- 显示可选标题、安全正文、优先级图标和“关闭”按钮；不展示原始 payload、坐标或内部 event key。
- `HIGH` 立即抢占正在显示的 `NORMAL`，被抢占普通通知回到最多 24 条的内存队列；同优先级按到达顺序展示。队列溢出时依次淘汰最早的 `NORMAL`、非安全 `HIGH`，仅当队列全部为安全事件时淘汰最早安全事件，以优先保留较新的安全提醒。
- 可见正文、合并后的 VoiceOver label 和 TTS 使用同一安全语义；关闭按钮提示会继续显示下一条。
- 活动订单的生命周期模板通知不直接展示/播报，由订单详情刷新后的本地状态文案替代。
- 派单 overlay 保持志愿者现有接受/拒绝和倒计时 UI，但数据源改为 app-lifetime retained prompt，导航不得重置后端截止时间。

**边界**：本层不提供分离操作、紧急操作、通知收件箱或后台推送。peer marker 仅按 `enable-live-escort-location-and-track-summary` 向当前订单双方开放。

## 实时同行位置组件

- 盲人订单状态页在状态、主要操作和“重复当前状态”之后展示志愿者辅助 marker；志愿者服务地图展示盲人辅助 marker。
- 仅接受匹配当前订单、角色方向正确、合法且不超过 15 秒的位置。过期后移除 marker，并显示“同行位置暂时不可用”。
- 每个角色页面至多保留一个同行位置过期任务；新样本取消旧任务，旧任务、错误订单和迟到样本不得清除更新后的 marker。页面离开、订单结束或切换订单时立即取消并清理。
- 禁止用动态 `.now` 的周期时间线检查新鲜度；无新位置、状态或用户交互时，同行位置组件不得周期性触发 SwiftUI/AttributeGraph 更新。
- 高频同行位置按订单与角色合并，每个主线程提交周期只交付最新样本；状态和通知事件保持可靠顺序，不因位置合并而丢弃。
- 辅助/背景地图不得拦截页面的垂直滚动手势，annotation 内容未变化时不得触发移除重加。
- 页面不得显示或朗读原始经纬度。地图 accessibilityLabel 只说明同行角色与位置新鲜度。
- `IN_PROGRESS` 显示“陪跑期间将持续使用定位，锁屏或后台仍会记录；服务结束后自动停止”，并显示权限、位置过期、网络间断和后台记录状态。

- 标题固定为“本次路线”，只绘制 `blindTrack`；地图位于状态和文字统计之后。
