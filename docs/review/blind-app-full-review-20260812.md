**日期**：2026-08-12

**配套调研**：[`docs/research/blind-app-feature-landscape-20260812.md`](../research/blind-app-feature-landscape-20260812.md)
**前一份 review**：[`frontend-backend-alignment-review-20260812.md`](./frontend-backend-alignment-review-20260812.md)（同日，聚焦前后端契约对齐；本份不重复其结论）

## 0. 结论摘要

**已经做得比大多数同类产品好的一件事**：VoiceOver 通道的深度。全仓 284 处 `accessibilityLabel`、152 处 `accessibilityHint`、50 处 `accessibilityElement(children:)`、5 处 `accessibilitySortPriority`，且遍历顺序与视觉顺序是**刻意解耦**并写明了理由的（`BlindRunnerHomeView.swift:497-515`）。这不是「加了标签」的水平，是「设计过遍历序」的水平。

**最应该先修的三件事**（详见 §3、§5）：

1. **打电话给志愿者直拨真实手机号**，后端的隐私号中转端点 `POST /api/orders/{orderId}/call/initiate` **零调用点**。双方真实号码互相永久暴露，而弱势一方是盲人。
2. **盲人端没有历史订单入口**，而 `AppState.swift:257` 的注释白纸黑字写着「跳过实名引导页进首页看历史订单和设置」—— 注释承诺的东西界面上不存在。
3. **横屏与 iPad 零适配**（`horizontalSizeClass` 全仓 **0** 命中），**业务事件零触觉反馈**（触觉只有 2 处、都在录音起停）。这两块打的都是低视力用户和「听觉通道被占用」的场景。

**最不该照抄竞品的一件事**：滴滴那套（优先派单、勋章、三节点提醒）看起来最像我们，但它的风险面是「找不到车」；我们的风险面是「一个陌生人和盲人在户外独处一小时」。功能清单要按 United In Stride 那一类对，不是按滴滴对。

## 2. 缺口分级：只留了接口的 vs 连接口都没有的

### 2.1 A 类 —— 后端接口已就绪，前端零调用点（可以立刻做）

对着 `origin/main` 的 65 条路径逐条比对，扣掉 `/api/cs/*`（8）与 `/api/admin/*`（4）这两组客服/管理端专用后，**前端未接的还有 8 条**：

| 端点 | 用途 | 未接的后果 | 判断 |
|---|---|---|---|
| `POST /api/orders/{orderId}/call/initiate` | **隐私号中转拨号** | 双方真实手机号互相暴露 | **P0，见 §3.1** |
| `GET /api/orders/{orderId}/call/records` | 通话记录 | 争议时无凭证 | P2，跟随上一条 |
| `GET /api/orders/{id}/status-logs` | 订单状态变更流水 | 盲人无法回溯「刚才到底发生了什么」 | **P1，见 §3.2** |
| `GET /api/orders/{id}/reviews` | 读取评价 | 只能写不能读；看不到志愿者过往评价 | P1 |
| `POST /api/orders/voice` | 语音直接下单 | — | 待确认，可能与 `voice/parse` 重复 |
| `POST /api/orders/voice/classify-query` | 语音意图分类 | 「问一句」的意图判定目前全在本地 | P2 |
| `POST /api/volunteer/location` | 志愿者位置上报（REST） | 志愿者端走 WS 上报，REST 通道未用 | P3，可能是冗余端点 |
| `GET /api/orders/available` | 可接订单池 | — | **刻意不接**，`MockAPIClient.swift:311` 有注释说明公开订单池链路已删除 |

> 核实方式：`git -C ../demo show origin/main:docs/api_spec.yaml` 取路径集，与 `blindRun/**/*.swift` 的字符串字面量 + 关键字双向比对。`keep-waiting` 一度被字面量扫描漏判（它走 `KeepWaitingEndpoint` 枚举拼接），关键字复查后确认**已接入**。

### 2.2 B 类 —— 前后端都没有（真正的功能空白）

按「对盲人的实际损失」排序：

1. **行程实时分享给紧急联系人** —— 家属只能在 SOS 触发后被动收到短信，跑步过程中完全看不到。这是网约车行业十年前就标配的东西。
2. **约定结束时间 + 超时告警** —— UIS 把「结束时间」列为出发前必须约定的四要素之一。我们连字段都没有。跑者失联时没有任何自动触发点。
3. **常用地址 / 收藏地点** —— 关怀版预存 10 个。对盲人，说地名是整个下单流程里最容易出错的一步（`disambiguate-same-name-start-place` 变更的起因就是真机上「阳光棕榈园」被定位到别的城市）。收藏地址能把这一步的错误率直接降到零。
4. **志愿者激励体系** —— 无积分、无勋章、无时长证明。志愿者供给是这类平台的生死线（UIS：每人需 6–8 名固定陪跑员）。
5. **固定搭档 / 收藏志愿者** —— 磨合成本是陪跑的核心成本，每单换人等于每单重新磨合。
6. **平台内文字/语音消息** —— 现在跑前沟通只能打电话。盲人打字成本高，但**收**文字消息（VoiceOver 朗读）成本很低。
7. **配速 / 距离能力字段** —— UIS 的四维筛选里有两维我们完全没有。
8. **新手引导 / 帮助中心** —— 全仓无教程、无帮助页。盲人首次使用一个语音优先 App 的学习成本被完全无视了。
9. **App 内客服/申诉入口** —— 后端 `/api/cs/*` 已备齐，但这是给客服坐席用的管理端，**用户侧的提交入口不存在**。
10. **无障碍身份标识透传给志愿者** —— 滴滴给司机弹「此订单乘客为盲人」。我们的志愿者端接单时是否显式知道对方是视障者、视障程度（`VisionLevel`）是几级、要不要带牵引绳，**没有专门的提示位**。

### 2.3 C 类 —— 已在 OpenSpec 排队（有计划，未做完）

| 变更 | 未完成 | 是什么 |

| `enable-cross-turn-voice-correction` | 5 | 跨轮语音纠错（改单项而非整句重说） |

## 3. 三个必须先修的问题（含证据）

### 3.1 P0：打电话直拨真实手机号，隐私号中转端点闲置

**证据**：`BlindOrderStatusView.swift:896-910`

```swift
let volunteerPhone = order.volunteerPhone?.nilIfBlank,
let telURL = EmergencyDialer.telURL(for: volunteerPhone) {
...
.accessibilityHint("拨打 \(volunteerPhone)，系统会先弹出拨号确认")
```

后端 `POST /api/orders/{orderId}/call/initiate` 与 `GET .../call/records` 在契约里，前端 **0 处**引用。

**为什么这是 P0 而不是 P2**：

- 陪跑关系是**长期且线下的**。志愿者拿到盲人的真实号码后，订单结束、账号删除都不影响他继续联系 —— 这与网约车「下车即断联」的风险模型完全不同。
- 调研里 UIS 的安全建议是「见面前交换电话」，但那是**双方自愿、自主决定**的交换。我们是**系统单方面把号码塞给对方**，性质不同。
- `accessibilityHint` 会把完整手机号念出来 —— 公共场合开外放的盲人用户，号码是被广播的。
- 一对一陪跑里志愿者可能就是威胁来源（这是 AGENTS.md §6 已经确立的前提，SOS 撤销权设计就基于它）。既然承认了这个前提，就不该把盲人的真实号码无条件交出去。

**修法**：拨号改走 `call/initiate` 返回的中转号；`volunteerPhone` 仅在中转不可用时降级，且降级要告知用户「本次通话将使用真实号码」。

### 3.2 P1：注释承诺了历史订单，界面上没有

**证据**：`AppState.swift:257` 注释「『稍后再说』：跳过实名引导页进首页看历史订单和设置」。但 `BlindRunnerHomeView.swift:575-622` 的 `homeSections` 只有：header / 加载态 / 错误态 / 活跃单或开始约跑 / 问一句 / 重复当前状态 / 位置摘要。**没有历史订单**。

盲人端对 `/api/orders/mine` 的唯一调用在 `BlindRunnerHomeView.swift:169`，用途是取活跃订单，不是列表。志愿者端 `VolunteerOrderFlowViews.swift:1639` 反而有完整列表。

**后果**：盲人无法回看「上次是谁陪我跑的」「上周跑了几次」，也无法对历史订单补评价。对一个**长期关系**产品，这等于把关系的记忆全部删掉了。这也直接堵死了 §2.2 里的「固定搭档」（没有历史，就没有「再约这个人」的起点）。

### 3.3 P1：低视力的视觉通道仍然是空白

这条在 `low-vision-visual-channel-unaudited` 记忆和上一份 review §D 已经记录过，本轮**复测数字如下**（全仓 grep，2026-08-12）：

| API | 命中 | 含义 |
|---|---|---|
| `horizontalSizeClass` | **0** | 横屏、iPad、分屏一律没有专门布局 |
| `sizeCategory` | **0** | |
| `differentiateWithoutColor` | **0** | 色觉障碍用户未被考虑（低视力常伴色觉异常） |
| `accessibilityRotor` | **0** | 无自定义转子 |
| `isVoiceOverRunning` | **0** | App 不知道用户开没开读屏 —— 这本身可以是设计选择，但意味着**「没开读屏的低视力用户」和「开了读屏的全盲用户」拿到的是同一套界面** |
| `dynamicTypeSize` | **1** | 仅 `HighContrastText.swift:45` 一处，且是**封顶** `...accessibility3`（系统最大是 AX5） |
| 触觉反馈 | **2** | 全部在 `SpeechInputService.swift:173/178`，服务于录音起停。业务事件（接单、志愿者到达、SOS 已发出、订单取消）**零触觉** |
| `accessibilityReduceMotion` | 4 | 全部在 `BlindBookingView.swift`，其余页面未响应 |

**触觉那条要单独说**：Apple 的指引明确「用户在看不见屏幕时最依赖触觉」。而陪跑场景恰恰是**听觉通道最容易被占用**的场景 —— 户外噪音、耳机在放音乐、正在跟志愿者说话。调研里 RunPacer 与 BLINDTRACK 两个研究项目的共同选择都是**振动触觉**，不是语音。我们把最重要的三条状态（志愿者已接单 / 已到达 / 求助已发出）全押在听觉上，是把鸡蛋放在最容易被打翻的篮子里。

`dynamicTypeSize` 封顶 AX3 违反 WCAG 1.4.4（200% 不裁切）—— AX3 相对默认约 175%，够不到 200%。

## 4. 哪些是后端的事，哪些是前端的事

用户问「是不是应该是后端的事情」。逐条分：

**纯前端，后端一行不用改**（可以今天就开工）：

- 隐私号拨号接线（端点已存在）
- 历史订单列表（`/api/orders/mine` 已存在且已分页）
- 读取评价 `GET /api/orders/{id}/reviews`
- 状态流水 `GET /api/orders/{id}/status-logs`
- 全部无障碍适配：横屏/iPad、Dynamic Type 放开到 AX5、对比度、触觉、转子
- 新手引导 / 帮助中心（纯本地内容）
- 常用地址（可以先做**纯本地**存储，见下）
- TTS 语速跟随 VoiceOver（`SpeechService.swift:41-44` 里已经把这事想清楚了，只差真机听一次定方案）

**必须后端先动**（前端做不了，要写进 handoff 等答复）：

- 行程分享给紧急联系人：需要分享令牌 + 只读轨迹端点 + 有效期
- 约定结束时间与超时告警：需要订单字段 + 定时任务 + 告警推送
- 志愿者激励体系（积分/勋章/优先派单）：完全是后端的派单与账务逻辑
- 固定搭档 / 收藏志愿者：需要关系表 + 派单时的偏好权重
- 配速 / 距离能力：数据模型 + 匹配算法
- 背景审查：外部征信/公安接口，是资质问题不是代码问题
- 用户侧客服工单提交：`/api/cs/*` 全是坐席侧，缺一条 C 端提交端点

**两边都要动**：

- 平台内消息：后端要消息表 + WS 通道，前端要会话 UI
- 「本单为视障跑者」的志愿者端提示：后端要在派单载荷里带 `VisionLevel` 与陪跑偏好，前端要给它一个显眼且不可跳过的位置
- 常用地址的**云端同步**：本地版前端可独立完成，跨设备同步需要后端

> **常用地址建议先做纯本地版**：`UserDefaults` + 一个结构体就能跑，不必等后端。它能直接压掉「说地名被定位到别的城市」这类事故（`disambiguate-same-name-start-place` 变更的起因）。等验证有用了再谈同步。

## 5. 全流程走查：从下载到跑完，哪里不顺

按一个真实盲人用户的顺序走一遍。每条都标了证据位置。

### 5.1 首次使用（最陡的一段）

| 步骤 | 顺不顺 | 问题 |
|---|---|---|
| 第一次打开 | ⚠️ | **没有任何引导**。这是一个语音优先的 App，但用户不知道「可以说话」这件事。全仓无 onboarding/教程 |
| 登录（手机号 + 验证码） | ✅ | 常规流程 |
| 角色选择 | ⚠️ | 盲人和志愿者共用一个 App。首次进来要先做一次「我是谁」的选择，对盲人是纯粹的额外一步 |
| 实名认证 | ⚠️ | **下单硬门槛**（后端 403）。要输姓名 + 身份证号 —— 对盲人是全流程里**打字成本最高**的一屏，且没有语音输入替代 |
| 「稍后再说」跳过 | ❌ | 跳过后进首页，但**首页没有历史订单**（注释说有，见 §3.2），也就是说跳过之后这个 App 对他**什么都做不了**，只有一个会失败的「开始约跑」 |
| 填资料 + 紧急联系人 | ⚠️ | `complete-blind-profile-and-contacts` 剩 2 项 |

**这一段是最大的流失点**。一个盲人用户从下载到能下第一单，要跨过：角色选择 → 实名（打字）→ 资料 → 紧急联系人，中间没有任何解释为什么。竞品里 Be My Eyes 是「装完直接能呼叫」，滴滴是「认证换优先派单」（认证是**增益**不是**门槛**）。

### 5.6 贯穿全程的两条

- **TTS 语速写死系统默认**。`SpeechService.swift:41-44` 的注释自己写清楚了：读屏用户日常把语速调到 14~16 字/秒，而合成器这边是默认速率。对熟练的读屏用户，App 的播报是**慢到难以忍受**的。注释里说「不靠读代码拍板，真机听过之后再定」—— 这件事该定了。
- **横屏 / iPad 完全没适配**（0 命中）。iPad Pro 是发布验证的两台设备之一。

## 7. 建议的开工顺序

按「盲人实际损失 ÷ 工作量」排，不按模块排：

**第一批（纯前端，端点都在，一周内可完）**

1. 隐私号拨号（§3.1）—— 唯一的隐私红线
2. 历史订单列表 —— 顺手把 `GET /reviews` 一起接，志愿者可核验
3. Dynamic Type 放开到 AX5 + 修已知的对比度 warning
4. 关键状态加触觉（接单 / 到达 / SOS 已发出 / 订单取消）
5. 常用地址本地版

**第二批（要产品拍板）**

6. 30 分钟提前量是否松绑（`EnvironmentConfig.swift:99`）
7. TTS 语速跟随 VoiceOver —— 需要真机听，然后定
8. 首次使用引导

**第三批（要后端）**

9. 行程分享给紧急联系人
10. 约定结束时间 + 超时告警
11. 志愿者激励与固定搭档

**同时要做的收尾**：9 个未归档 OpenSpec 变更里，先判 `capture-and-gate-runner-extra-needs` 与 `enable-one-utterance-booking` 会不会 delta 同一个能力，再动手。
