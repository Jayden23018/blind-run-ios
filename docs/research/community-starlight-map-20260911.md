# 「星光地图」：中国地图上的用户分布点亮图

**日期**：2026-09-11 · **档位**：C（完整选型，三线并行）
**问题**：可缩放中国地图 + 志愿者/盲人注册点亮一个发光点 + 夜间星座质感 + 点亮动画。技术路线怎么走、合规不合规、效果什么样。

---

## 0. 一句话结论

**视觉和技术都能做，但有一道必须先过的行政门槛（地图审核 + 审图号），和一条必须改掉的设计（盲人的点不能按个体上图）。**
另有一个不依赖任何技术的产品前提：**这个功能的情绪效果与用户规模强绑定，在内测规模下效果是反的。**

## 1. 🔴 合规：这是一道行政审批门槛，不是技术问题

### 1.1 App 内的可缩放中国地图属于「互联网地图服务」，必须送审

> 第二条：在中华人民共和国境内从事向社会公开的地图的编制、审核、出版和互联网地图服务以及监督检查活动，应当遵守本条例。

[《地图管理条例》](https://www.gov.cn/zhengce/zhengceku/2015-12/14/content_10403.htm) [高]

免审例外**不覆盖我们这个形态**：

> 《地图审核管理规定》第六条：下列地图不需要审核：（一）直接使用自然资源主管部门提供的具有审图号的公益性地图；（二）景区地图、街区地图、公共交通线路图等内容简单的地图；（三）法律法规明确应予公开且不涉及国界、边界、历史疆界、行政区域界线或者范围的地图。

[《地图审核管理规定》](https://www.gov.cn/zhengce/2019-08/13/content_5711407.htm) [高]

一张能看到全国省界、可缩放的中国地图，既不是「内容简单」，也不是「不涉及行政区域界线」。

### 1.2 用高德的底图**不转移**合规责任

这条是本轮最反直觉、也最要紧的发现。高德自己的合规指南逐字写着：

> 高德软件有限公司是依据《中华人民共和国测绘法》……依法申请并持有互联网地图服务甲级测绘资质的公司。……**开发者应落实安全主体责任**，确保在登载使用地图时准确反映中国领土范围、行政区域界线、重要岛屿等并标示审图号；引用地图时要注明地图来源和审图号。**若开发者计划对所调用的地图内容进行修改的，请注意依法履行地图审核程序。**

[高德开放平台开发者合规指南](https://lbs.amap.com/compliance-center/check-and-reference/compliance)（更新于 2025-12-03）[高]

并且高德保留对违规开发者「收回服务使用权限、暂停或终止服务、关闭账号、保存记录并上报」的处置权。

### 1.3 2024 年有一份专门针对 App 的联合通知

> （一）依法履行行政审批。从事互联网地图服务的APP主办者应按照……《地图管理条例》等规定，向自然资源主管部门、电信主管部门履行地图审核程序、ICP备案手续。
> （三）加强监管。针对登载使用地图的APP存在「应当送审而未送审的……未在地图的适当位置显著标注审图号的」等违法违规行为，自然资源主管部门将会同电信主管部门对APP主办者依法采取处置措施。

[自然资办函〔2024〕972号](https://www.gov.cn/zhengce/zhengceku/202405/content_6950568.htm) [高]

### 1.5 自绘 GeoJSON 边界是更危险的路，不是绕开的路

> 第十条：在地图上绘制中华人民共和国国界……应当遵守下列规定：（一）中华人民共和国国界，按照中国国界线画法标准样图绘制……

[《地图管理条例》](https://www.gov.cn/zhengce/zhengceku/2015-12/14/content_10403.htm) [高]

《公开地图内容表示规范》（自然资规〔2023〕2号）对台湾、南海断续线、钓鱼岛、克什米尔逐条规定画法，例如：

> 八、台湾省地图表示规定：（一）台湾省在地图上应当按省级行政单位表示……（二）台湾省地图的图幅范围，应当绘出钓鱼岛和赤尾屿

[《公开地图内容表示规范》](https://www.gov.cn/gongbao/content/2023/content_5752310.htm) [高]

2018 年国家测绘地理信息局通报的第一批 8 起「问题地图」典型案件，全部是自制/自绘地图：

> ——「无印良品」商店登载「问题地图」案：……该地图无审图号，存在错绘国界线，漏绘钓鱼岛、赤尾屿和南海诸岛等重要岛屿，海南岛与大陆不同色，台湾岛注记错误等严重错误。

[新华网转发通报](http://www.xinhuanet.com/politics/2018-01/29/c_1122336938.htm) [高]

⚠️ 开源中国 GeoJSON 数据的状态（技术线实测）：`longwosion/geojson-map-china` 313 star / **最近 commit 2015-07-13（10 年未更新）/ 无 license**。这类数据多衍生自第三方公开服务，不是官方测绘成果 —— 拿它画国界，风险敞口在我们这边。

### 1.6 🚩 现状核查：本仓库当前已有一个欠着的合规项

```
全仓搜索「审图号 / GS( / 测绘 / 地图数据版权」：0 处
```

我们**现在就在 App 里展示高德地图**（首页、订单、轨迹回放），但没有任何审图号标注。这不是新功能引入的问题，是既有缺口。新功能只是让它从「工具性地图」变成「向社会公开展示的内容性地图」，更难辩解。

- **仅调色（自定义地图样式，不改边界）是否触发重新送审**？同样没有官方口径。**[未找到一手依据]**

## 2. 🔴 隐私：Strava 军事基地事件在我们身上会更严重

### 2.1 事故本体

2018 年 1 月，安全研究者发现 Strava 全球热力图在阿富汗、叙利亚等人烟稀少地区，意外勾勒出美军秘密基地的巡逻路线 —— 因为那些区域的运动数据几乎全部来自驻军人员。

> "Strava heatmap can be used to locate military bases"

[WIRED](https://www.wired.com/story/strava-heat-map-military-bases-fitness-trackers-privacy/) [高]

**机制**：聚合在低背景噪声区域**会退化成逐人定位**。这不是「显示得不够模糊」，是聚合这个手段本身在小基数下失效。

### 2.2 为什么在 AidRun 会更严重

三个因素叠加，而且每一个都比 Strava 当年更糟：

1. **我们的用户基数就是小的** —— 内测期全国几十人。Strava 是在偏远地区才退化，我们是**全国都处在退化区**。
2. **被点亮的是视障人士** —— 「某地有一个盲人」是可反推的健康状况，PIPL 下的敏感个人信息。而 `VisionLevel` 在我们数据模型里是一等公民。
3. **产品需求直接指向可反推的粒度** —— 原话是「志愿者放大的时候就能看到自己附近具体有多少人」。能数清人数的缩放级别，就是能定位到个体的级别。

放大到街区级、某栋楼上有一个琥珀色的点 = 公开「这里住着一个视力障碍者」。对这个群体这是实打实的人身安全暴露面（定向盗窃、诈骗）。

同类形态的监管注意度也在上升：Snap Map / Instagram Map 的逐用户定位点反复引发警方与国会关注（[NBC](https://www.nbcnews.com/tech/tech-news/instagram-maps-feature-raises-privacy-concerns-some-users-rcna223706) [高]、[Forbes](https://www.forbes.com/sites/conormurray/2025/08/07/what-to-know-about-instagrams-new-map-feature-and-why-its-sparking-privacy-concerns/) [高]）。

### 2.3 结论（这条不是建议，是红线）

**视障用户的位置不得以个体粒度上图。** 可行的替代：

- 只上**志愿者**的点（且同样做聚合下限）
- 盲人一侧改成**计数而非点位**：「你所在的城市有 37 位志愿者」
- 若一定要表达「还有别的盲人跑者」，最细粒度到**城市**，且设最小基数阈值（k-匿名，k 至少 5，低于阈值的区域不显示而非显示 1）

顺带：这个改法**同时更贴合产品意图**。盲人要的情绪是「有人愿意帮我」，不是「还有别的盲人」。

## 3. 技术路线：高德海量点是唯一同时满足合规与性能背书的路

### 3.1 候选对比

| 方案 | iOS 16 | 夜间星空 | 万级点 | 合规底图 | 迁移成本 |
|---|---|---|---|---|---|
| **高德 `MAMultiPointOverlay`** | ✅ 5.1.0+（我们 11.1.200） | ✅ 需自建样式 | ✅ 官方称至 10 万 | ✅ 已集成 | **低** |
| MapKit + `MKClusterAnnotation` | ✅ iOS 11+ | ❌ **出局** | ⚠️ 几百个就有性能报告 | ⚠️ 无法定制 | 中 |
| SwiftUI Canvas / Metal 自绘 | ✅ | ✅ 完全自主 | ❓ 无量化证据 | ❌ 需自备 GeoJSON | 高 |
| WKWebView + deck.gl/Mapbox | ✅ | ✅ | ✅ | ❓ 未调研 | 高 |

**MapKit 直接出局**：`MKStandardMapConfiguration.EmphasisStyle` 只有 `.default` 和 `.muted` 两个 case，做不出星空质感。[Apple 官方](https://developer.apple.com/documentation/mapkit/mkstandardmapconfiguration) [高]

### 3.2 高德海量点的两个硬约束（直接影响需求的两个点）

官方原文：

> 海量点图层支持处理的点数量级跨度较大，从几十个点至十万个点（建议不超过100000个点数据）都可以应用海量点图层进行处理。该功能自 iOS 地图 SDK 5.1.0 版本起开始支持。

[绘制海量点图层](https://lbs.amap.com/api/ios-sdk/guide/draw-on-map/mass-points-overlay) [高]

🚩 **约束一 —— 「点亮动画」在这个图层里做不了**：

> 点对象集合（注意：**MAMultiPointItem属性不支持动态更新**）

items 一旦创建不可就地改，要点亮某个点必须重建整个 overlay。

🚩 **约束二 —— 一个 overlay 内所有点共用一张 icon**：

> 注意：为了保证渲染效率，**纹理不受alpha参数影响**，如果需要设置透明度，请更换icon。

做不到逐点独立的发光强度或呼吸动画。

**修法（不是障碍，是分层）**：海量点图层画「所有既有用户」的静态星空（志愿者一个 overlay、盲人一个 overlay，两张 icon），刚注册的那一个点用**单个普通 `MAPointAnnotation`** 单独画，动画只发生在这一个 annotation 上。一帧只有一个动画元素，开销可忽略。

### 3.3 自定义样式怎么来

必须先在高德「自定义地图平台」后台设计并发布，拿 `styleId`（在线）或下载 `.data`（离线），客户端用：

```
- (void)setCustomMapStyleOptions:(MAMapCustomStyleOptions *)styleOptions;  // since 6.6.0
```

`MAMapCustomStyleOptions` 属性：`styleData` / `styleExtraData` / `styleTextureData` / `styleId`。
平台可定制 7 大类 44 种元素（区域面、建筑物、水系、天空、道路、标注、行政边界）。
[自定义地图 - iOS 地图SDK](https://lbs.amap.com/api/ios-sdk/guide/create-map/custom) [高]

⚠️ **没有现成的「星空」预设**，要自己调。另：7.0.0 起样式格式变过一次，旧样式文件需重新导出。

### 3.4 聚合：高德**没有**内置 cluster 类

常见说法「高德 SDK 有 `MAAnnotationCluster`」在 API Reference 里查无此类 —— 那是官方**开源 Demo 工程里的示例代码**（四叉树 + 自写 `ClusterAnnotation`）。[SDK 示例](https://lbs.amap.com/demo/sdk/cluster-marker) [中]

Swift 生态里真正在维护的聚合库只有一个：

| 库 | star | 最近 commit | License |
|---|---|---|---|
| `efremidze/Cluster`（QuadTree） | 1295 | 2025-07-08 | MIT |
| `Rightpoint/BentoMap` | 182 | 2017-02-15 ⚠️9 年 | MIT |
| `pawelmajcher/SwiftyH3` | 20 | 2026-08-12 | Apache-2.0 |

**没有 Supercluster 的 Swift 移植**（只有 Python/Rust）。

**服务端聚合 vs 客户端聚合**：全国到街道级跨越多个数量级，把全量坐标下发到端上跑四叉树在流量和内存上不现实。业界生产系统（Mapbox、Google `GMUHeatmapTileLayer`）都是服务端按 zoom bucket 预聚合。⇒ **这个功能必须有后端配合，不是纯前端能做完的。**

### 3.5 后端现状：零数据源

`demo/docs/api_spec.yaml` 共 101 个端点，**没有任何**用户分布 / 区域统计 / 附近人数类接口。按 AGENTS §4，iOS 侧实现必须留在明确的契约后面，需要新增至少：

```
GET /api/community/density?zoom={z}&bbox={minLng,minLat,maxLng,maxLat}
→ [{ gridId, centerLng, centerLat, volunteerCount, runnerCount }]
```

且服务端必须执行 k-匿名下限（见 §2.3），**不能把下限交给客户端** —— 客户端过滤等于数据已经下发过了。

## 4. 视觉参考：同类产品怎么做的

### 4.1 最接近的参照是 GitHub Globe，不是 Strava

**Strava Global Heatmap 形态不对** —— 它是**轨迹密度**，不是「每人一个点」。它的发光来自「浅色 = 更热」的反转色阶，在深底图上天然产生发光错觉，不需要 bloom。[Strava 官方](https://support.strava.com/en-us/articles/16046277-a-guide-to-strava-heatmaps) [高]

**GitHub Globe 才是对口的**：约 12,000 个小圆点构成大陆轮廓，自定义 shader 画光晕消除锯齿，**帧率低于 55.5 FPS 时把圆点数从 12,000 降到 8,000**（四档质量分级）。
[How we built the GitHub globe](https://github.blog/engineering/engineering-principles/how-we-built-the-github-globe/) [高]

可直接在浏览器里操作的最接近 demo：
- https://vasturiano.github.io/globe.gl/example/world-population/ （深色地球 + 人口密度发光分布）
- https://vasturiano.github.io/globe.gl/example/heatmap/

globe.gl 默认背景 `#000011`，点默认 `#ffffaa`。

### 4.2 视觉规格共识

- **底图不是纯黑**，是深灰/近黑，留少量灰度给道路边界当 context（Mapbox Dark、globe.gl `#000011`）
- **发光两条路**：反转色阶（Strava，零特效开销）／ 真实 bloom shader（GitHub Globe，纯装饰开销，需要性能降级预案）
- **密度处理三种**：聚合成热力 ／ 保留逐点但 LOD 降采样（GitHub 的做法）／ 逐点 + 语义配色（Life360）
- Mapbox Gallery 里现成的深色样式可当调色参考：Dark 2D、Moonlight、**Neon Glow**、**NASA's Black Marble**（夜间灯光卫星图，本身就是「发光点分布」的现实原型）—— https://www.mapbox.com/gallery [高]

### 4.3 🚩 领域内的空白点（对我们有利）

**助盲跑同类产品目前都是纯功能地图，没有一家做情绪化表达**：

- United In Stride：Find a Partner 是标准 pin + 列表，红色图钉代表引导志愿者，无深色主题无动画。https://www.unitedinstride.com/find-a-partner [高]
- GoodSAM：急救响应者网络地图，同样纯功能。https://www.goodsamapp.org/ [高]
- Be My Eyes：**没有**志愿者分布地图，只有里程碑数字新闻稿

⇒ 这个想法在本领域是空白的，不是抄别人。

## 5. 🔴 产品前提：效果与用户规模强绑定，且小规模下是反的

本轮自建了一个密度模拟（中国 40 个主要城市真实坐标按人口权重撒点）：

| 规模 | 观感 |
|---|---|
| 40 人（内测真实规模） | 全国十来个孤点，传达的是「原来只有这么几个人」 |
| 400 人 | 能看出城市簇，但仍稀疏 |
| 3,000 人 | 开始有「片」的感觉 |
| 20,000 人 | 东部连成带 |
| 120,000 人 | 中国轮廓从光点里浮出来 |

对照 GitHub Globe 用 12,000 点画地球轮廓、deck.gl 英国道路事故图用 140,100 点画出英国轮廓 —— **「点自己组成地图」这个效果需要万级以上的点。**

⇒ 在拿到那个量级之前，这个功能要么不上，要么**改成不依赖密度的表达**（例如只显示「你周边 N 公里内有 X 人」+ 一圈近邻光点，不显示全国空图）。

## 6. 🔴 无障碍：这个功能对全盲用户目前价值为零

需求原话是「盲人也能感觉到身旁是有人的」，但**全盲用户看不到这张图**。本仓库两条无障碍通道里，这个功能只落在视觉那条（而那条从没被系统性验收过，见记忆 `low-vision-visual-channel-unaudited`）。

而且按既有结论，装饰性地图在本仓库是要 `accessibilityHidden` 的（[swiftui-voiceover-traversal-order-20260814](./swiftui-voiceover-traversal-order-20260814.md)）—— 也就是说这张图对 VoiceOver 用户**默认就是不存在的**。

⇒ 要做，必须同时做听觉等价物，且它才是盲人端的主体：
> 「你所在的城市，有 37 位志愿者。最近的一位在 1.2 公里内。」

一句话，比一整张图对全盲用户有用得多 —— 而且**它不需要地图，因此不需要审图号，也不泄露任何人的位置**。

## 7. 共识 vs 争议

### 共识（多源印证）
- App 内可缩放中国地图需履行地图审核程序、标注审图号 [多条法规 + 2024 联合通知，高]
- 使用有资质厂商的 SDK 不免除开发者自身的合规义务 [高德自己的合规指南逐字，高]
- 深色底图 + 亮色点是这类可视化的行业通行视觉语言 [Mapbox/GitHub/Strava 一致，高]
- 大规模点位聚合应在服务端按 zoom 预计算 [Mapbox/Google 生产做法，中]

### 争议 / 未决
| 争点 | 各方 | 状态 |
|---|---|---|
| 在合规底图上叠加自有点位是否构成「修改地图内容」 | 高德指南暗示「修改内容需重新送审」；条例第三十八条要求对「新增内容核查校对」，但都没点名叠加点位这一形态 | **无官方定性，必须问自然资源主管部门** |
| 仅调色是否触发送审 | 同上 | **无官方口径** |
| 标准地图可否矢量化二次开发 | 技术博客说「编辑改动后公开使用需送审」；官方条款原文抓不到（JS 单页应用） | [低]，不可作为依据 |
| Canvas 自绘的真实性能 | 社区教程称 `.drawingGroup()` 约 3× 提升；Apple 论坛有 250 个矩形规模「毫无帮助」的反例 | **无可复现基准，两方都是经验** |

## 8. 反对意见（什么情况下上面的建议是错的）

1. **如果产品接受「只做城市级聚合、永不下钻到街道」**，那么 §2 的隐私红线大部分消失，§1 的合规门槛可能也能绕开 —— 因为一张只有「北京 37 人 / 上海 52 人」气泡的示意图，可能落进「内容简单」的免审例外。此时正确方案不是高德海量点，而是**一张静态的合规底图 + 几十个气泡**，成本降一个数量级。本报告的技术选型建立在「要能放大到街道级」这个需求上，需求一改结论就变。

2. **如果这个功能只对内（运营看板 / 路演演示），不进 App 发布版**，则地图审核、审图号、PIPL 全部不适用（不是「向社会公开」）。若真实目的是路演时展示「我们覆盖了多少地方」，做成一张**导出的图片或 H5**比做进 App 便宜得多，也没有任何合规敞口。**动手前应当先确认这一条** —— 它会直接否掉整个 iOS 实现。

3. **如果后端不愿意新增聚合端点**，整条路线不成立。客户端不可能从现有 101 个端点里拼出用户分布，也不该把全量用户坐标下发到端上。

4. **如果 §5 的规模判断被真实数据推翻**（例如产品实际预期是接入某个已有的百万级志愿者库），那么「小规模下效果是反的」这条前提消失，可以直接按 §3 的方案做。

## 10. 落地建议（若决定做）

按依赖顺序，不可并行：

1. **先确认 §8.2**：这功能是进 App 还是只对内。只对内 → 本报告到此为止，做张图即可。
2. **产品/法务判定 §1.7 的两个未定论**，必要时向自然资源主管部门咨询。**在拿到答复前不写代码。**
3. 顺带补上 §1.6 的既有缺口（现有地图页左下角标注审图号）—— 这件事**与本功能无关，独立成立，应当先做**。
4. 后端新增密度聚合端点，k-匿名下限在服务端执行。
5. iOS 侧：高德自定义样式（后台调深色）+ `MAMultiPointOverlay` 两个 overlay（志愿者/盲人分桶）+ 单个 `MAPointAnnotation` 承载点亮动画。
6. 同期做听觉版（§6），且它应当**先于**视觉版上线 —— 它对盲人端的价值更高、成本更低、零合规敞口。
