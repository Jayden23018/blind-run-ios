# 盲人端视觉 UI 对标：从真实产品截图反推我们的首页与接单后页面

调研日期 2026-08-08 ｜ 只谈**视觉 UI 与信息密度**，交互契约、语音、错误码不在本篇
上一篇 [`blind-voice-booking-ia-20260805.md`](./blind-voice-booking-ia-20260805.md) 定的是**信息架构与焦点数**，
本篇定的是**每个焦点长什么样、占多大、写几个字**。两篇不冲突，本篇是它的视觉落地层。

**一手材料**：`docs/ui/reference-screenshots/` 下 11 个产品 64 张 App Store 官方截图，
用 iTunes Lookup API 于 2026-08-08 抓取（`https://itunes.apple.com/lookup?id={trackId}`）。
下面每条结论都能在这些像素上直接核对，不是转述别人的博客。

---

## 0. 一句话结论

用户的判断（「字太多、按钮还是小、这些字对盲人没用」）**全部成立**，而且比想象的更严重：

- 首页主按钮现在是 `minHeight: 64`（`BlindRunnerHomeView.swift:713`），Be My Eyes 的同位按钮**占内容区约 75%**。
  差的不是一点，是**一个数量级的视觉权重**。
- 但用户草图里的**圆形**大按钮是错的方向 —— 同样外接尺寸下圆形只有 π/4 ≈ **78.5%** 的可点面积，
  且逼着文字换行缩号。**所有对标产品无一例外用全宽圆角矩形。**
- 草图里并排的两个「常用」chip 也要改成**上下两行全宽** —— 对标产品的次级操作**没有一个是并排的**。
- 真正没被处理的是**接单后**那页：现在 7 个 section 竖着堆，
  而小艾帮帮的通话中页面**整页只有一张头像和一个按钮**。

## 1. 六条可对着像素核对的规则

### 规则 1：首屏只有一个动作，它是一整块面积，不是一个「按钮」

**证据**：`reference-screenshots/be-my-eyes/03.png`

Be My Eyes 首页（v7.12.0，2026-06 更新）自上而下只有三样东西：

| 元素 | 占屏比 | 内容 |
|---|---|---|
| `Call a volunteer` 蓝色圆角矩形 | 内容区约 **75%** | **只有这五个字**。无图标、无副标题、无说明 |
| `My groups >` 描边行 | 约 8% | 全宽 |
| 底部 5 tab | 约 10% | — |

**注意它没有什么**：没有顶部标题栏、没有「当前位置」、没有欢迎语、没有插画、按钮里没有图标。

> **这条对全盲用户没有点击收益** —— VoiceOver 选中后在屏幕任意位置双击都能激活，物理面积不参与激活。
> 它服务的是**低视力用户**和**没开读屏的用户**（我们的 B 类）。上一篇 §0 结论一已经论证过，
> 这次的截图是它的视觉实证：连 Be My Eyes 这种全盲优先的产品也认为这块面积值得付出。

### 规则 2：全宽圆角矩形，不要圆形

用户草图用的是圆形。三个理由反对：

1. **可点面积损失 21.5%**（π/4）。四个角是纯浪费。
2. **圆形逼着文字缩号换行**。草图里「语音输入目的地」在圆里挤成两行 + 一行英文，
   矩形铺满宽度可以一行放下并且字号大一倍。
3. **对标产品零例外**：Be My Eyes（矩形）、Aira（矩形卡）、GoodMaps（全宽色条）、
   Lazarillo 登录页（四个全宽矩形）—— 没有一个用圆。
   Aira 在矩形卡**内部**放了个圆形图标，那是装饰，不是触达区。

### 规则 3：次级操作是「整行铺满」的竖直堆叠，绝不并排

**证据**：`reference-screenshots/aira-explorer/02.png`

Aira 首页主卡下面是三行**全宽等高**的描边行：
`Attach Message or Files` / `Browse Access Offers` / `Configure Devices`。

草图里「常用：奥森公园 ｜ 常用：家附近」并排两个 chip 要改。除了宽度砍半，还有一个隐性问题：
**两个视觉上同一行的元素，VoiceOver 遍历顺序取决于框架布局而非视觉直觉**，
横排是本项目 UI 测试假失败的常见来源。改成上下两行，顺序才是确定的。

顺带：文案里的「常用：」是冗余前缀，读屏会把它读两遍（两行都读）。直接写「奥森公园」「家附近」。

### 规则 4：一行只放两个信息 —— 左边一个名字，右边一个数字

**证据**：三个产品同构

| 产品 | 截图 | 行的形态 |
|---|---|---|
| WeWALK | `wewalk/01.png` | `Limoncello Restaurant` ／ `116 meters` + `Slightly right` |
| Lazarillo | `lazarillo/04.png` | `North De Anza Boulevard & Mariani Avenue` `Bus Stop` ／右对齐 `587 ft` |
| GoodMaps | `goodmaps/02.png` | 全宽黄条：左 `Start Walking`，右 `96 ft` |

**没有一行是「标签：值」的完整句。** 对比我们的订单卡（`BlindRunnerHomeView.swift:783-791`）：

```
预约时间：2026-08-10 07:30
出发地点：朝阳公园东门
志愿者电话：138****1234
```

每行都带「xxx：」前缀，读屏念出来长度翻倍，而这三个前缀在上下文里都是废话 ——
一个陪跑订单里出现的时间就是预约时间，出现的电话就是志愿者的。

### 规则 5：地图是装饰，列表是界面

**证据**：`lazarillo/04.png` —— 地图压在顶部约 30%，下面全是文字行；`goodmaps/02.png` 同构。

**这条我们已经做对了**（`mapBackgroundLayer` + `allowsHitTesting(false)` + `accessibilitySortPriority(-1)`，
`BlindRunnerHomeView.swift:446-461`）。**保持，不要改。**

### 规则 6：进行中页面 = 一个身份 + 一个巨大动作

**证据**：`reference-screenshots/xiaoai-bangbang/02.png`（小艾帮帮通话中）

整页元素：志愿者头像（圆形，约屏宽 40%）→ 一个确认弹窗 →
**一个占屏宽 85% 的「通话挂断」胶囊按钮**。没有第三个东西。没有「服务进行中，请与志愿者保持沟通」这种话。

我们的 `BlindOrderStatusView` 现在是 7 个 section 竖着堆
（`statusHeader` → `peerMapSection` → `lifecycleSection` → `volunteerSection` → `orderInfoSection`
→ `actionSection` → `debugMockControls`，`BlindOrderStatusView.swift:540-546`）。

## 2. 现有文字逐条裁决

裁决三档：**删**（视觉与读屏都去掉）／**降级**（视觉删，内容进 `accessibilityHint`）／**留**。

### 首页

| 现有文字 | 位置 | 裁决 | 理由 |
|---|---|---|---|
| 「准备好后，可以创建一次新的陪跑预约。」 | `:697` | **降级** | 说明按钮要干什么 → 这正是 `accessibilityHint` 的定义。低视力用户看按钮本身就够 |
| 「正在后台同步当前状态，页面仍可使用」 | `:526` | **降级** | 上一篇已裁「并入 header 的 `accessibilityValue`」，视觉上缩成一个不占行的小转圈 |
| 「位置摘要」标题 | `:631` | **删** | 下面那行位置描述本身就自解释；标题是给视觉扫读用的，这里没有扫读 |
| 位置描述正文 | `:637` | **留但降权** | `docs/09:78` 硬性要求「地图的文字等价物必须在地图之外可用」，不能删。缩成一行 caption |
| 「开始约跑」 | `:708` | **留并放大** | 见下节 |
| 「重复当前状态」 | `:743` | **留** | 项目硬规则 + 已有断言 `AccessibilityAuditTests.swift:84-98` |

### 接单后（订单状态页）

| 现有文字 | 位置 | 裁决 | 理由 |
|---|---|---|---|
| 「请与志愿者保持沟通，注意安全。系统会持续同步订单状态，服务完成后进入评价页面。」 | `:684` | **删** | 33 字。「系统会持续同步订单状态」是实现细节，「完成后进入评价页面」是还没发生的事。**盲人跑步时听这句要 6 秒，且没有一个字能让他做出任何动作** |
| `statusHeader` 的 `blindRunnerDescription` 副标题 | `:631` | **降级** | 与主标题语义重复，上一篇已裁「合并容器」。合并后读一遍，不是两遍 |
| 「等待志愿者开始服务」+ `arrivedWaitingCopy` | `:661-665` | **合并为一行** | 标题与正文说的是同一件事 |
| 「志愿者信息」标题 | `:823` | **删** | 同「位置摘要」 |
| 「志愿者电话：138****1234」 | `:829` | **改形态** | 这是当前页面**最重要的一个动作**却是一行只读文字。见 §3.2 |
| 「预约信息」整块 `orderInfoSection` | `:849` | **收进二级** | 服务进行中时，出发地点/时长/备注都是已经不可改、也不需要再听的信息 |
| 「同行位置」地图 | `:767-790` | **留但对读屏隐藏** | 同首页地图规则 5 |

## 3. 目标布局

### 3.1 首页（无订单态）

```
┌────────────────────────────┐
│  [地图装饰 ≈30%]            │  accessibilityHidden，右上角浮 64×64 设置齿轮
├────────────────────────────┤
│  你还没有预约                │  一行。进页面自动 Announcement
│                            │
│  ┌──────────────────────┐  │
│  │                      │  │
│  │                      │  │  ← 全宽圆角矩形
│  │      开始约跑         │  │     高度 ≥ 内容区 55%（≈360pt @ 6.1"）
│  │                      │  │     字号 ≥ 44pt（@ScaledMetric）
│  │                      │  │     无图标、无副标题
│  └──────────────────────┘  │
│                            │
│  ┌──────────────────────┐  │
│  │  奥森公园             │  │  ← 全宽行，各自独立一行
│  └──────────────────────┘  │
│  ┌──────────────────────┐  │
│  │  家附近               │  │
│  └──────────────────────┘  │
│  ┌──────────────────────┐  │
│  │  重复当前状态          │  │  序位钉死（WCAG 3.2.6）
│  └──────────────────────┘  │
│  朝阳公园东门附近            │  ← caption，地图的文字等价物
├────────────────────────────┤
│  ██  SOS 紧急求助  ██       │  常驻，形态不变
└────────────────────────────┘
```

**焦点数 5**（状态行 / 开始约跑 / 常用×2 / 重复当前状态 / 位置 caption ——
常用地址若为空则 3 个），与上一篇 §4.1 的目标一致。

> **一个必须决掉的文案问题**：草图写的是「语音输入目的地」，代码里是「开始约跑」。
> Be My Eyes 的标签是 `Call a volunteer` —— 描述**结果**，不是**输入方式**。
> 「语音输入目的地」把机制暴露在最显眼的位置，而机制是我们的实现细节。
> **建议保留「开始约跑」**，把「按下后可以直接说目的地」放进 `accessibilityHint` 和按下后的第一句播报。

### 3.2 接单后：按状态给四种形态，每种只有一个主动作

现在这页对所有状态用同一套 7 个 section。改成状态驱动的单动作页：

| 状态 | 大字一句话（≥34pt） | 一个数字 | **唯一主按钮**（全宽，≥120pt 高） | 次级（全宽行） |
|---|---|---|---|---|
| `PENDING_MATCH` / `PENDING_ACCEPT` | 正在找志愿者 | 已等待 3 分钟 | 取消预约 | 重复当前状态 |
| `DRIVER_EN_ROUTE` | 张伟正在赶来 | 还有 800 米 | **打电话给张伟** | 重复当前状态 ／ 取消 |
| `DRIVER_ARRIVED` | 张伟已到达 | 距你 20 米 | **打电话给张伟** | 重复当前状态 |
| `IN_PROGRESS` | 陪跑进行中 | 已跑 2.4 公里 | —（此状态下 SOS 条即主动作） | 重复当前状态 |
| `REMATCHING` | 正在重新匹配 | 已等待 1 分钟 | 取消预约 | 重复当前状态 |
| `COMPLETED` | 本次陪跑已完成 | 共 5.1 公里 | 提交评价 | 返回首页 |

**「打电话给志愿者」必须升为主按钮，这是本篇最硬的一条改动建议。** 三条外部证据：

1. 202 名视障者问卷 + 12 人访谈的研究结论：导航阶段用户最优先的信息是
   **「车的型号／怎么找到正确的那一辆」** —— 即**识别与汇合**，不是 ETA 也不是地图
   （[ScienceDirect S107158192500151X](https://www.sciencedirect.com/science/article/abs/pii/S107158192500151X)）。
2. Guide Dogs for the Blind 给视障乘客的操作建议原文要点：接单后记下姓名/车辆/车牌/ETA，
   **并在接驾前几分钟主动打电话**说明自己站在哪、无法用眼睛找到对方
   （[guidedogs.com/rideshare](https://www.guidedogs.com/rideshare)）。
3. **我们的场景没有车牌、没有车型、没有颜色** —— 陪跑志愿者是个人，
   视障者手里**唯一的汇合手段就是这通电话**。把它做成「志愿者信息」卡片里的一行只读文字，
   等于把唯一的出路藏起来。

**同时要补的两件事**（属新能力，需先走契约与需求，不在本篇的改版范围内）：

- **接近阈值的触觉冗余**：研究反复指出路边噪音环境下语音播报听不见，
  haptic + 空间音频的多模态方案在准确率与完成时间上都优于纯音频。
  建议 `DRIVER_ARRIVED` 与 50m 阈值各给一次 `UINotificationFeedbackGenerator`。
  （上一篇已提 50m 播报，后端 `ESCORT_DISTANCE_ALERT` 是信息性提示，不等于这个能力。）
- **「让对方找到我」**：视障者不仅要找到志愿者，更需要**被找到**。
  最省的做法是一个「播报我的位置描述」按钮，用 GCJ-02 逆地理编码生成一句可复述的话术
  （不得念经纬度，`docs/09:79`）。

## 5. 本篇没做的事

- **没有改任何代码。** 首页与订单页的改版会动到 `enable-one-utterance-booking` 与
  `enable-live-escort-location-and-track-summary` 两个未归档的 OpenSpec 变更所覆盖的能力，
  按 `AGENTS.md` §4 要先确认 spec 再动手。
- **没有验证「大按钮对低视力用户的实际收益」** —— 这需要真人测试，上一篇 §10.2 已列为待测项。
- **触觉冗余与「让对方找到我」是新能力**，需求与后端契约都还没有，本篇只记录证据。
- 引用的三条 ride-hailing 研究结论**转述自搜索结果摘要，未逐篇读原文**；
  作为改动依据前建议人工复核 ScienceDirect 那两篇的样本与结论原文。
