## Context

盲人跑者的下单成本是本轮产品评估的核心问题。评估过程做了两件事：读代码确认下单的真实门槛，以及调研盲人专用 App 的既有实践。

**代码事实**：预约页的三项必填信息里，两项已有可用默认值。`BlindBookingViewModel.resolvedStartPlace`（`BlindBookingView.swift:352`）在 `selectedStartPlace` 与 `currentResolvedPlace` 都为空时会用设备当前位置合成一个 `ResolvedPlace`，只要 `locationService` 存在就永远非 nil；`configure`（`:382`）把 `appointmentTime` 抬到 `minimumAppointmentTime + 60`，即天然满足 30 分钟提前量；跑步需求六项全部选填。因此 `canSubmit`（`:208`）在进页面时即为 `true`。今天让用户说满三轮，其中两轮是在复述系统已经准备好的值。

**调研事实**：跳过确认环节的纯语音执行在盲人场景有明确的已知翻车模式（语音购物研究记录了「用户说出特定商品、系统用通用确认回应了完全不同商品」的真实案例，原因是设计假设「用户会瞄一眼屏幕核对」，而这个假设对盲人不成立）。同时纯分步表单也不是答案——ACM 研究显示盲人用户偏好连续指令，反感每一步重新触发。**证据指向的是「一次说完 + 强制语音复述确认」的混合模式**，而不是两个极端中的任何一个。

**缺陷**：评估中核对语音授权路径时发现 `SpeechInputService.clearRecognitionStartState(marking:)`（`:325`）清空 `completionHandler` 而不调用它。五条启动失败路径共用它，因此 `VoiceOrderWizard` 的完成回调永不触发。

## Goals / Non-Goals

**Goals**

- 让「默认即可成单」这个已经成立的事实对用户可达：一句肯定词完成下单。
- 保住确认环节。语音复述 + 显式肯定，不做静默执行。
- 修根因，让所有语音启动失败路径都能抵达向导的既有降级逻辑。
- 零后端改动，零契约变更。

**Non-Goals**

- 不改盲人首页布局与按钮数量（后续变更）。
- 不引入即时约跑。30 分钟提前量是后端硬约束（`APPOINTMENT_TOO_SOON`，`EnvironmentConfig.swift:99`），属派单模型问题。
- 不做 App Intent / Siri 快捷指令。
- 不改 SOS 任何行为。

## Decisions

### 1. 确认判定用本地保守白名单，不新增后端解析

`ParseSlotRequest` 只有 `startTime` / `duration` 两个槽位（`VoiceOrderWizard.swift:230,246`），没有 confirm。为一次「是/否」判定新增端点、契约与后端排期，不成比例。

更重要的是**这一判定不需要语义理解**：需要的是一个高精度的肯定词识别，而不是一个高召回的意图分类器。本地白名单在这件事上不比大模型差，且没有网络往返、没有 8 秒超时窗口、没有弱网失败态。

**已知天花板**（在代码中以 `ponytail:` 注明）：白名单覆盖不了的方言与长句表达会被判为「非确认」，用户因此多说两轮。这个方向的失败是可接受的；反方向不是。等真实使用数据显示误判率高到值得处理，再考虑接后端。

### 2. 白名单必须保守，因为两个方向的错误代价不对称

- 「确认」被误判为「非确认」→ 用户多说两轮话。**可恢复，代价低。**
- 「修改」被误判为「确认」→ 产生一张用户没打算下的订单，会触发真实派单。**代价高。**

因此：只有明确肯定词进入提交路径，**其余一切**（否定、听不清、空白、歧义、超时、识别错误）一律进入逐项流程。不做模糊匹配、不做前缀匹配、不做「包含肯定词即算」——「不确认」「先别确认」这类表达含有肯定词但意思相反。

兜底：提交后有「订单提交成功」播报，且订单可由盲人取消（`RunOrderStatus.canBlindRunnerCancel`）。

### 3. 缺陷修在 `clearRecognitionStartState`，不在五个调用点

五条失败路径（授权 ×2、recognizer 不可用、音频会话失败、麦克风输入不可用）全部经过这一个函数。在每个调用点补一次回调是五处改动、五处可能漏，且下一个新增的失败路径会再漏一次。在共同出口修一次，全部调用者自动受益——这同时也是最短的 diff。

回调需幂等：`clearRecognitionStartState` 可能在一次会话中被调用多次（`beginRecognition:338` 与 `startRecognition:204/214` 都会调），必须保证同一 session 只发一次终局完成。用清空前取出局部引用再置 nil 的顺序保证。

### 4. 新首步放进 `VoiceOrderWizard`，不新建组件

向导已经拥有需要的一切：TTS 与录音的时序协调（`waitForSpeechToSettle`）、重问计数与三次降级、`fallBack` 的必须播报约定、以及对 `BlindBookingViewModel` 的引用。新建一个并行组件会把这些全部复制一遍，并制造第二条需要各自维护的语音路径。

新首步之后的 `.startPlace → .startTime → .duration → .review` 一步不改。「说了『修改』」与「今天点了语音下单」走的是同一段代码。

### 5. 本批次不动首页

新首步经由现有「语音下单」按钮的 `.voiceBooking` 路由（`BlindRunnerHomeView.swift:410-416`，已 `startsWithVoice: true`）即可完整验证。首页布局改动需要真机开 VoiceOver 手测，与本批次的纯逻辑改动验证成本差一个量级；混在一起会让真机批跑失败时无法定位是哪一半的问题。

### 6. `start()` 的前置检查只挡「已知不可用」

不主动申请权限、不预先探测麦克风——那会把权限弹窗从「用户说了要用语音」的时刻挪到更早，反而更突兀。只在已经能确定语音不可用时（如此前会话已判定授权被拒）跳过重问循环直接进表单。其余情况仍走正常路径，由决策 3 修好的终局回调兜底。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 「修改」误识为「确认」产生非预期订单 | 保守白名单（决策 2）、提交后播报、订单可取消 |
| 白名单漏掉常见口语表达，用户被迫多说两轮 | 可接受方向的失败；单测锁定每一条白名单词；留 `ponytail:` 注明升级路径 |
| 用户没听清整单就说了确认 | 读回三段式（原话 + 整单 + 出路）同时给出「改地点 / 改时间 / 改时长」；`repeatCurrentPrompt()` 已存在且在读回轮可用 |
| 定位尚未就绪时起点是演示坐标 | **未解**：读回会念出实际起点，但不阻断提交（tasks 2.10）。演示坐标绝不会进 `resolve-address`/`parse` 的消歧参数——拿它去消歧会把人约到另一座城市 |
| 用户说了地点但后端抽不出，静默落回当前位置 | **未解**：`missing: ADDRESS` 分不出「没说」和「说了没抽出」（tasks 2A.8）。暂靠读回念出实际起点兜底，已提给后端 |
| 修改完成回调波及其他语音输入调用方 | `SpeechInputField` 的其他使用者（地点搜索、备注、评价等）此前在启动失败时同样收不到回调，本修复对它们是净改善；需回归既有 `SpeechInputService` 用例 |

## Open Questions

1. **`missing: ADDRESS` 的歧义**（等后端，handoff 2026-08-04）：整句抽不到地址时，「用户根本没说地点」用当前位置是对的，「用户说了但后端抽不出 span」用当前位置会把人约到错误起点。请求后端在 `missing` 里区分，或加一个「检测到地名但解析失败」的标志。在此之前客户端不猜。
2. **演示坐标是否阻断提交**（等产品，tasks 2.10）：语音与表单两条路径都只播报不阻断，属既有行为。
