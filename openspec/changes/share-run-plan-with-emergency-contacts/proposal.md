## Why

**家属现在只有在出事之后才知道这次跑步存在。**

当前唯一会触达紧急联系人的通道是 SOS：`POST /api/emergency/trigger` 之后，后端在事务提交后
**异步**发短信（`EmergencyContactNotifier.java:60-62`），失败只播给客服、**从不回告盲人**
（`:126-135`）。也就是说——跑步开始、跑到一半、正常结束，家属全程零可见性；等到有可见性的时候，
已经是求助了。

United In Stride 把**开始时间 / 集合地点 / 路线 / 结束时间**列为陪跑出发前必须约定的四要素
（`docs/research/blind-app-feature-landscape-20260812.md` §2.2）。AidRun 这四项数据**全都有**，
只是没有任何一条出口通向家属。

**实时分享后端正在做，前端要迈的是「同意」这道坎。**（2026-08-13 修订，见下）

本变更立项时核过后端 `origin/main`：`docs/api_spec.yaml` 全文 `share` 零命中，
`/api/orders/{id}/track` 的鉴权写死「JWT 用户必须是该订单的盲人或志愿者一方」
（`api_spec.yaml:1839-1881`），紧急联系人不是账号、拿不到。当时的结论是「服务端那半截前端做不了」。

**那个结论在同一天被后端的在途工作追上了。** 后端在分支 `feat/trip-share-link` 上做了：

| 方法 | 端点 | 说明 |
|---|---|---|
| POST | `/api/orders/{id}/share` | BLIND，返回 `{shareUrl, expiresAt}`，**幂等** |
| DELETE | `/api/orders/{id}/share` | 停止分享，已发出的链接立刻失效 |
| GET | `/api/share/{token}` | **免登录**，家属侧分享页自己调，客户端不接 |

家属侧页面（`/share.html`）也是后端的，前端**只需要把 `shareUrl` 丢进系统分享面板**。

⚠️ **但这批改动截至本变更修订时仍未提交**：后端仓库工作区里 `api_spec.yaml` / `handoff.md`
等 7 个文件是 ` M` 状态，`git log -S 'orders/{id}/share' --all` 对实现零命中，
`origin/main` 的契约里 `share` 仍然零命中。按 `AGENTS.md` §11 的口径，
**不基于未提交的契约写调用代码**。

**于是本变更的落点变成两块**：

1. **静态行程告知（已实现）** —— 把行程要素交给系统短信，零端点。它不是实时分享的替代品，
   而是它的**降级路径**：断网、`POST /share` 失败、订单已终态（后端返 409）时，
   家属仍然能收到出发时间和地点。
2. **明示同意（本次实现）** —— 这一块**不依赖任何契约**，现在就能做完并验收。
   后端通报里点名这是客户端的责任：

   > 调这个接口 = 盲人对「向持链接者提供**本人实时位置与轨迹**」的单独同意
   > （PIPL 第 23 条向第三方提供 / 第 29 条敏感个人信息，轨迹属第 28 条明列的「行踪轨迹」）。
   > **做成一键静默分享，这个同意在法律上不成立**——后端挡不住这一层，只有你们能。

## What Changes

- 盲人订单状态页在**所有非终态**提供「把这次行程告诉家人」动作，与后端 `POST /share`
  的口径一致（含 `PENDING_MATCH`——家属看到「正在找志愿者」也是有意义的）。
  终态**隐藏**入口而不是禁用：后端对终态返 409 `SHARE_ORDER_ALREADY_FINISHED`，
  摆一个按下去必然报错的按钮对读屏用户是纯噪音。
- 动作打开系统短信 composer，收件人预填**主紧急联系人**，正文预填出发时间、起点、
  预计结束时间、终点（仅当 `endAddress` 非空）、订单号。
- **不调用任何新端点**，不新增网络请求，不改订单状态机。
- composer 关闭后按 `didFinishWithResult:` 播报结果，文案锁定在「已交给系统短信」这一侧。
- 设备不能发短信（`canSendText == false`）时如实告知并给出替代路径，不静默失败。
- **明示同意**：首次分享实时位置走全屏告知页（三条告知各自是独立的 VoiceOver 焦点），
  之后每次一句话确认；同意**按用户 + 按告知版本**记录，文案一改旧同意自动失效。
  拒绝不劝、不重试、不藏入口。

## 非目标（明确不做，不是漏做）

- **本次不接 `POST` / `DELETE /api/orders/{id}/share`**。契约还在后端工作区里没提交，
  接了既验不了，也等于把别人的 WIP 烘进本 PR。后端合入 `main` 后单独接，
  届时同意流程与状态门控已经就位，只剩两个调用。
- **不自动发送、不自动分享**。Strava Beacon 的关键闸门就是「Beacon 开着 ≠ 联系人能看到，
  不发那条短信联系人什么也收不到」——发送权始终在用户手里。这一条在实时分享上更硬：
  自动分享 = 没有单独同意。
- **不把令牌从 fragment 挪走**。后端把 token 放在 `share.html#<token>` 而不是 query，
  是因为 fragment 不进 Referer、不上服务端日志，而分享页要加载高德 JS SDK 这个第三方脚本。
  客户端拿到 `shareUrl` 原样传递，不重新拼链接。
- **不请求让家属看到志愿者位置**。志愿者是第三方，盲人无权替他同意 ——
  与「志愿者手机号盲人同意不了」是同一条线。后端分享内容本身也不含志愿者坐标、
  只有掩码姓名（`李*`）。
- **不做超时告警**（功能 6）。`plannedEnd` 已在契约里，但「超时没结束就告警」需要后端定时任务，
  客户端本地通知在 App 被杀死时不可靠，拿它当安全兜底是错觉。单独立项。

## 一条必须逐字守住的红线

`MFMessageComposeViewController` 的 delegate 回调 `.sent` **不保证消息真的到达收件人**
（Apple 文档，`docs/research/live-trip-sharing-and-volunteer-incentives-20260813.md` §3）。
这与 `AGENTS.md` §6 那条 SOS 文案红线是**同一类问题**：

- 允许说：「短信已交给系统，请在短信 App 里确认已发出」
- **禁止说**：「已通知家人」「家人已收到」「已送达」——一个字都不行

用户还可以在系统界面里改掉收件人和正文，改完之后内容不再由 App 掌控，这是第二个不能宣称送达的理由。

## 回后端的两个问题（2026-08-13 通报点名要答）

> ⚠️ 答复**尚未**写进 `demo/docs/handoff.md`：那个文件当前是后端同事的未提交工作区
> （` M` 状态），现在写会跟他的 WIP 打架。等 `feat/trip-share-link` 合入 `main` 后立即投递。

1. **明示告知做成什么形态** —— **首次全屏引导页 + 之后每次简短确认**。
   全屏而不是对话框，是因为系统对话框的 VoiceOver 遍历会把 message 当成一整块念完，
   用户中途想回到第二条没有着力点；全屏页里三条各自是独立焦点，右滑一次一条。
   之后不重复全文：每次都念长文本，用户会开始跳过它，那才是真正失去告知效力的时候 ——
   但简短确认里保留「任何拿到链接的人都能看到」这条最有意外性的。
   同意按**用户 + 告知版本**记录，文案一改旧同意结构性失效。
2. **入口放哪、什么状态** —— 盲人端订单状态页，**非终态全给，与你们一致**（含 `PENDING_MATCH`）。
   终态**隐藏**而不是禁用，理由就是你们说的那个 409。

## 需要后端确认的

1. **`OrderDetailResponse` 没有志愿者身份字段**（核 `origin/main` 契约：只有 `volunteerPhone`，
   无姓名、无工号，前端全仓 `volunteerName` 零命中）。家属收到一条不含陪跑者身份的告知短信，
   安全价值大打折扣——UIS 的建议正是「见面前先交换电话号码」。
   注意这与分享页不同：分享页你们已经给了掩码姓名（`李*`），但**短信降级路径拿不到它**。
   请确认是否能在订单详情里补一个可对外披露的志愿者标识（掩码姓名即可，与分享页同一口径）。
2. **志愿者手机号能不能写进发给第三方的短信**？本变更**默认不写**（见 `design.md` D5）：
   志愿者没有同意把号码给盲人的家属，且隐私号至今未开通（handoff `5798` 未答）。
   这与你们那条「志愿者是第三方，盲人无权替他同意」是同一条线，我们按同一口径处理。
3. **`expiresAt` 的语义**：是绝对过期时间，还是随订单生命周期动态延长？
   对标产品（Strava Beacon / Uber）一律绑行程生命周期而非固定 TTL。
   客户端要不要在到期前提示用户续期，取决于这一条。
