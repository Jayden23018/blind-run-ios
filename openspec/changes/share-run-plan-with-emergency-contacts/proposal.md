## Why

**家属现在只有在出事之后才知道这次跑步存在。**

当前唯一会触达紧急联系人的通道是 SOS：`POST /api/emergency/trigger` 之后，后端在事务提交后
**异步**发短信（`EmergencyContactNotifier.java:60-62`），失败只播给客服、**从不回告盲人**
（`:126-135`）。也就是说——跑步开始、跑到一半、正常结束，家属全程零可见性；等到有可见性的时候，
已经是求助了。

United In Stride 把**开始时间 / 集合地点 / 路线 / 结束时间**列为陪跑出发前必须约定的四要素
（`docs/research/blind-app-feature-landscape-20260812.md` §2.2）。AidRun 这四项数据**全都有**，
只是没有任何一条出口通向家属。

**实时分享做不了，这次不做。** 核过后端 `origin/main`：

- `docs/api_spec.yaml` 全文 `share` **零命中** —— 没有分享令牌，没有免登录只读页
- `/api/orders/{id}/track` 的鉴权逐字是「JWT 用户必须是该订单的盲人或志愿者一方」
  （`api_spec.yaml:1839-1881`），紧急联系人不是账号，拿不到

而 Strava Beacon 与 Uber Share My Trip 是同一套架构：**服务端发 token + 托管免登录只读页，
客户端只负责把链接塞进预填短信让用户手动发**（`docs/research/live-trip-sharing-and-volunteer-incentives-20260813.md` §1）。
服务端那半截前端做不了——客户端没有公网可达地址，也没法让一个没有账号的人读订单数据。

**客户端能独立闭环的恰好是最后那一步**：把一段行程文本交给系统短信，由用户自己点发送。
去掉「实时」，剩下的就是 UIS 四要素的**静态告知**——它解决的是「家属根本不知道这件事在发生」，
而这正是当前缺口里最大的一块。

## What Changes

- 盲人订单状态页在 `PENDING_ACCEPT` / `DRIVER_EN_ROUTE` / `DRIVER_ARRIVED` / `IN_PROGRESS`
  四态提供「把这次行程告诉家人」动作（`PENDING_MATCH` 不给——还没人接单，没有可告知的内容）。
- 动作打开系统短信 composer，收件人预填**主紧急联系人**，正文预填出发时间、起点、
  预计结束时间、终点（仅当 `endAddress` 非空）、订单号。
- **不调用任何新端点**，不新增网络请求，不改订单状态机。
- composer 关闭后按 `didFinishWithResult:` 播报结果，文案锁定在「已交给系统短信」这一侧。
- 设备不能发短信（`canSendText == false`）时如实告知并给出替代路径，不静默失败。

## 非目标（明确不做，不是漏做）

- **不做实时位置分享**。缺后端契约，见上。本变更的 tasks 里含投递该契约需求的一条。
- **不自动发送**。Strava Beacon 的关键闸门就是「Beacon 开着 ≠ 联系人能看到，不发那条短信
  联系人什么也收不到」——发送权始终在用户手里。自动发送还会踩下面那条红线。
- **不做超时告警**（功能 6）。`plannedEnd` 已在契约里，但「超时没结束就告警」需要后端定时任务，
  客户端本地通知在 App 被杀死时不可靠，拿它当安全兜底是错觉。单独立项。

## 一条必须逐字守住的红线

`MFMessageComposeViewController` 的 delegate 回调 `.sent` **不保证消息真的到达收件人**
（Apple 文档，`docs/research/live-trip-sharing-and-volunteer-incentives-20260813.md` §3）。
这与 `AGENTS.md` §6 那条 SOS 文案红线是**同一类问题**：

- 允许说：「短信已交给系统，请在短信 App 里确认已发出」
- **禁止说**：「已通知家人」「家人已收到」「已送达」——一个字都不行

用户还可以在系统界面里改掉收件人和正文，改完之后内容不再由 App 掌控，这是第二个不能宣称送达的理由。

## 需要后端确认的

1. **实时行程分享的完整契约**（本变更的真正终局，请排期）：分享令牌生成端点、
   免登录只读页、令牌失效时机（对标产品一律绑行程生命周期而非固定 TTL）、
   联系人数量上限（Strava 3 个 / Uber 5 个，我们的 `blind-identity-and-contact-management`
   已定义 1–5 个联系人）、以及跑步结束后只读页展示什么。
2. **`OrderDetailResponse` 没有志愿者身份字段**（核 `origin/main` 契约：只有 `volunteerPhone`，
   无姓名、无工号，前端全仓 `volunteerName` 零命中）。家属收到一条不含陪跑者身份的告知短信，
   安全价值大打折扣——UIS 的建议正是「见面前先交换电话号码」。
   请确认是否能在订单详情里补一个**可对外披露**的志愿者标识（姓氏 + 平台编号即可，不需要全名）。
3. **志愿者手机号能不能写进发给第三方的短信**？本变更**默认不写**（见 `design.md` D5）：
   志愿者没有同意把号码给盲人的家属，且隐私号至今未开通（handoff `5798` 未答）。
   若产品侧认为应该写，需要先有志愿者侧的授权口径。
