# 设计

## D1. 静态告知与实时分享的分工（2026-08-13 修订）

初版这一节的标题是「这一版为什么是静态告知**而不是**实时分享」，理由是后端零基础。
后端在同一天把三个端点做出来并合入 `origin/main`（`fdbc4ee`，#86），所以两者不再是二选一：

| | 实时分享 | 静态告知（短信） |
|---|---|---|
| 依赖 | `POST` / `DELETE /api/orders/{id}/share` | 无 |
| 家属看到 | 实时位置 + 轨迹，随行程结束失效 | 一条不会更新的文本 |
| 前置 | **必须先有明示同意**（PIPL） | 不需要（用户自己发的静态文本，不构成向第三方持续提供位置） |
| 何时用 | 主路径，常驻 | 降级路径，**实时分享失败后才露出** |

**短信入口不常驻。** 两个都摆着，读屏用户每次都要多滑一个按钮去分辨哪个是他要的 ——
而在实时分享可用时，静态文本从来不是他想要的那条。失败时再露出，用户此刻正需要一条别的路。
`canSendText == false` 的设备连降级入口都不给：摆出来等于把人支上一条同样走不通的路。

**同意只挂在实时分享上，不挂在短信上。** 给短信也加一道同意页是错误的合规理解：
用户自己在系统短信里发一段静态文本，既不是自动化的第三方提供，也不含实时位置。
多这一道只会让盲人多听一段跟他要做的事无关的长文本。

实时分享的服务端那三样东西客户端做不了，这一段仍然成立（也正是后端做那三个端点的原因）：

| 需要什么 | 为什么客户端做不了 |
|---|---|
| 一个公网可达的 URL | 客户端没有公网地址 |
| 一个不需要登录就能读订单的页面 | 紧急联系人不是账号；`/api/orders/{id}/track` 写死了「必须是订单双方」 |
| 令牌的签发与失效 | 签发方必须是持有数据的一方 |

客户端在对标产品架构里承担的**只有最后一环**：把链接塞进预填短信。把那一环单独拿出来、
链接换成静态文本，就是本变更——它是最终形态的**真子集**，不是替代方案，后端契约到位后
只需把正文里多加一行 URL，UI、状态门控、无障碍播报、红线文案全部复用。

**被否掉的替代方案**（留档，理由比结论值钱）：

- **前端起个本地 HTTP 服务**：手机没有稳定公网地址，NAT 后不可达，且会被系统在后台杀掉。
- **iOS 系统「共享我的位置」/ Find My**：没有公开 API，App 无法编程发起。
- **每隔 N 分钟自动发一条位置短信**：家属被短信轰炸，且发送权被 App 拿走后，
  下面 D3 那条红线守不住（App 不知道每条有没有发出去）。

## D2. 状态门控：非终态全给，与后端一致（2026-08-13 修订）

| 状态 | 给不给 | 为什么 |
|---|---|---|
| `PENDING_MATCH` | ✅ | 后端口径：家属看到「正在找志愿者」也是有意义的。初版排除它的理由是「订单可能被自动取消，家属拿到会失效的信息」——**那条理由不成立**：链接幂等，订单取消后家属看到的是 `410`（曾经有效但已结束），不是一条无限期的坏链接 |
| `PENDING_ACCEPT` | ✅ | 已派给具体志愿者，行程要素齐了 |
| `DRIVER_EN_ROUTE` / `DRIVER_ARRIVED` | ✅ | 出发前告知的正常时机 |
| `IN_PROGRESS` | ✅ | 跑到一半想起来要告诉家人，这条路不能堵 |
| `REMATCHING` | ✅ | 非终态。志愿者取消后仍在重新匹配，行程还在 |
| `COMPLETED` / `CANCELLED` / `NO_VOLUNTEER` | ❌ **隐藏** | 终态。后端返 409 `SHARE_ORDER_ALREADY_FINISHED`，摆一个按下去必然报错的按钮对读屏用户是纯噪音——所以是隐藏，不是禁用 |
| `unknown` | ❌ | 分不清是不是终态，猜错的代价是让盲人按下一个必然 409 的按钮 |

判定写成**穷举 switch** 而不是 `if 包含在数组里`——与 `offersVolunteerCall` 同一套写法。
穷举的价值在后端加新状态时：`switch` 编译不过，数组写法会静默把新状态归到「不给」。

## D3. 文案红线：三处文本，一个字都不能松

`.sent` 不代表送达，用户还能改收件人和正文。因此：

| 位置 | 文案 |
|---|---|
| 按钮 | `把这次行程告诉家人` |
| 按钮 a11y hint | `打开短信，内容已经填好，需要你自己点发送` |
| `.sent` 后播报 | `短信已交给系统，请在短信里确认已发出` |
| `.cancelled` 后播报 | `已取消，没有发送` |
| `.failed` 后播报 | `短信没能发出，请稍后再试或直接打电话` |

**禁止出现**的措辞：已通知、已收到、已送达、家人已知悉。这条与 `AGENTS.md` §6 同源，
按 §1.1 落成守卫（见 `tasks.md` 2.4），不靠人记。

## D4. 无障碍：系统 composer 是 out-of-process，播报只能自己做

`MFMessageComposeViewController` 跑在**独立进程**，App **无法**往里注入 `accessibilityLabel`、
traits 或自定义转子——那棵无障碍树归 Apple。所以：

- composer 内部的可访问性不归我们管，也管不了，不要试图 hack。
- **composer 关闭这件事，盲人用户没有任何感知**——看不到 sheet 收起，也看不到结果。
  必须在 `didFinishWithResult:` 里主动播报（D3 那三条），不播等于没有反馈。
- 播报走既有的 `SpeechService`，不新起 TTS 通道。

## D5. 短信正文里放什么、不放什么

**放**（全部来自 `OrderDetailResponse`，核过后端 `origin/main` 契约确实存在）：

| 内容 | 字段 | 缺失时 |
|---|---|---|
| 出发时间 | `plannedStart` | 整句省略该项 |
| 起点 | `startAddress` | 整句省略该项 |
| 预计结束时间 | `plannedEnd` | 整句省略该项（**不要**用 `plannedStart + expectedDurationMinutes` 自己推——两者口径可能不一致） |
| 终点 | `endAddress` | **`nil` 时一个字都不许提终点**。`nil` 的含义是「用户未指定终点」，不是「原路返回」，两者混淆会让家属去等一个盲人从没说过的地点（`OrderModels.swift:308-311` 已有硬口径） |
| 订单号 | `orderId` | 必有 |

**不放**：

- **志愿者手机号**（`volunteerPhone`）。志愿者没有同意把号码给盲人的家属；隐私号至今未开通
  （handoff `5798` 未答），现在放进去就是把真实号码给第三方。默认关闭，产品侧要开需要
  志愿者授权口径先落地。
- **志愿者姓名 / 工号**：契约里**根本没有这两个字段**（`OrderDetailResponse` 只有 `volunteerPhone`），
  不是我们选择不放，是拿不到。已投 handoff（proposal 第 2 条）。
- 盲人自己的手机号、健康信息、`specialNotes`、`visionLevel` —— 家属都知道，写进去只增加泄露面。

## D6. 收件人：默认主联系人，允许改，不做多选

`blind-identity-and-contact-management` 已经保证了**主联系人不变式**（1–5 个联系人，恒有一个 primary）。
直接取 primary 作为预填收件人，用户在系统界面里可以自己加人或换人。

不做 App 内多选：系统 composer 在 iOS 14.2 上约 10 个收件人就会出现渲染错乱
（Apple 开发者论坛实测），而我们最多 5 个联系人——问题不在上限，在于**多选 UI 是一屏额外的
VoiceOver 遍历**，换来的能力系统界面本来就有。

**没有联系人时**：不隐藏按钮（隐藏了盲人不知道有这功能），按下去引导到紧急联系人管理页。

## D8. 明示同意：为什么是全屏页、为什么记版本号

**全屏页而不是对话框。** 系统对话框的 VoiceOver 遍历会把 message 当成一整块念完，
用户中途想回到第二条没有着力点。全屏页里三条告知各自是独立焦点，右滑一次一条、可以停、
可以回头再听。这不是排版偏好，是这段文本**能不能起到告知作用**的差别 ——
一段听完就忘、回不去的文本，在合规上和没告知没有区别。

对应的代码约束写在 `RunPlanShareConsentView` 里：那个 `VStack` 上**不许**加
`.accessibilityElement(children: .combine)`，加了就把三条并成一段，正好回到对话框的问题。

**之后每次只给一句话确认。** 每次都念全文，用户会开始跳过它 —— 那才是真正失去告知效力的
时候。但简短确认保留「任何拿到链接的人都能看到」这条：它是三条里唯一有意外性的，
用户默认以为只有自己发给的那个人能看。

**同意按「用户 + 告知版本」存。** 两个维度缺一不可：

- 按用户：同意是个人作出的，换账号登录不继承。同一台手机换人用不罕见，
  视障用户的设备常由家人协助设置。
- 按版本：`RunPlanShareConsentCopy` 的告知内容一改，旧同意就没有覆盖到新内容。
  版本号进 key（`runPlanShareConsent.v1.<userId>`），改文案时 bump 版本，旧记录**结构性失效** ——
  靠人记「改了文案要清同意」必然漏，而漏掉的后果是拿旧同意去覆盖新告知，
  正是 PIPL 上不成立的那种同意。
  `RunPlanShareConsentTests.testDisclosureVersionCoversEveryDisclosure` 用**字面断言**钉住
  三条文案：改文案这条就红，红了先 bump 版本再改断言。刻意不用 hash/长度/关键词等聪明写法 ——
  那些可能在文案实质改变时仍然通过。

**拒绝按钮和同意按钮一样大、一样整行铺满。** 把拒绝做小、做成一行浅色文字，
对低视力用户是一个找不到的出口，对读屏用户则是最后才遍历到的东西。拒绝后不劝、不重试、
不把入口藏起来 —— 拒绝是一个完整的答案。

**判定与展示分开**：`RunPlanShareConsentStep.next(hasGivenConsent:)` 是纯函数，
「首次没走全屏引导」这种缺陷在 UI 里几乎测不出来，在这里是一行断言。

## D7. 并发模型：只有 async/await，没有 Combine

静态告知那半边**不发任何网络请求**，数据全部来自订单状态页已经持有的 `OrderDetailResponse`。
实时分享那半边只有两个 `await` 调用（`POST` / `DELETE`），走 `Task {}`，
不新增 `AnyCancellable` —— `AGENTS.md` 那条「同一条数据流不许既订阅 Combine 又 await async」
在这里的姿势是：**新代码一律 async/await**。

`isWorkingOnLiveShare` 是两个请求共用的一道闸：重复点击会打出两个并发 `POST`，
而后端的幂等是「顺序调用幂等」，并发到达时可能各生成一个链接（契约里逐字写着）。
两个都有效、`DELETE` 会一次性撤销全部，所以不是正确性问题，但没必要制造它。

纯函数那部分（`RunPlanShareMessage.compose` / `RunPlanLiveShareMessage.compose` /
`RunPlanLiveShareStore`）是全部可测逻辑的所在地，用单测钉死，不需要 UI 测试。

## D9. 分享状态存在客户端，是后端缺口的临时补丁

`/api/orders/{id}/share` 只有 `POST` 和 `DELETE`，**没有 `GET`**，`OrderDetailResponse`
里也没有任何分享状态字段（核过 `origin/main` 契约的 required 列表）。于是「这一单是不是
正在分享」这个事实在客户端只能靠自己记。

不记的后果不是体验问题：告知页第三条逐字承诺「你可以随时停止分享」，而链接在服务端能活到
`max(plannedEndTime, now) + 2h`。App 被杀一次，承诺就静默失效 —— 链接还在外面有效，
用户再也找不到停止的入口。所以 `RunPlanLiveShareStore` 写 `UserDefaults`。

**只存一个订单号，不是每单一个 key。** 盲人同一时刻只可能有一个进行中的订单
（后端 `DUPLICATE_ORDER` 挡着），按单存会在 `UserDefaults` 里堆下无上限、没人清的历史 key。
这个 key 进 `AppStatePersistenceKeys.all`，登出时随 `reset()` 清掉 —— 漏掉的话，
下一个登录的人会看到「停止分享」，而那是上一个账号的链接，他既停不掉也不该知道它存在。

**停止失败时不清本地状态**：链接可能还有效，把入口一起收走等于再也停不掉。
宁可让用户多按一次。

已向后端提出补 `shareActive` / `shareExpiresAt`（proposal「需要后端确认的」第 4 条），
补上后这个类可以整个删掉。
